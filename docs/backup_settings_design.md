# Version 2.2 バックアップ設定・状態表示 詳細設計案

## 1. 目的と前提

Version 2.2では、最後のバックアップを確認し、自分でバックアップを作成でき、自動バックアップ間隔と保持世代数を安全に設定できるようにする。バックアップ保存先の変更、常駐スケジューラ、クラウド同期は対象外とする。

現行`BackupService`の既定値は24時間・10世代。自動作成は`create_backup_if_needed()`、間隔を問わない作成は`create_backup()`、復元は復元元を検証した後に現在DBを強制バックアップする。現行の世代整理は新規ファイルの作成直後に行われ、復元元を`protected_paths`で保護する。新しい仕様でもこれらの契約を維持する。

## 2. 設定の仕様

| 項目 | 既定値 | 許容範囲 | 画面上の単位 |
| --- | ---: | ---: | --- |
| 自動バックアップ間隔 | 24 | 1～168 の整数 | 時間 |
| 保持世代数 | 10 | 2～100 の整数 | 件 |

上限は異常な入力を避けるための案。下限2件は通常の世代整理で、直近のバックアップに加えて過去の別世代を残すために採用する。既存ファイルを設定変更だけで削除しない。利用者が入力した前後の空白は許容するが、負数、小数、空文字、文字列、真偽値などは拒否する。設定画面では現在有効な設定と保存した設定を区別する。「保存した設定は次回起動時に自動・手動バックアップへ適用」と明記し、実行中の`BackupService`の設定を不意に変更しない。

保存先は`ApplicationPaths.root_directory / "backup_settings.json"`を提案する。実際のパスは`ApplicationPaths`に読み取り専用プロパティとして追加し、`BOOK_MANAGER_HOME`による保存先の差し替えと既存のデータ移行に従う。JSONの例は次のとおり。

```json
{
  "schema_version": 1,
  "backup_interval_hours": 24,
  "max_backups": 10
}
```

APIキーやDBの内容は保存しない。ファイル不在なら既定値を使用する。形式不正・未知のスキーマ・読み込み失敗ではエラーを記録して利用者へ通知し、バックアップ設定を勝手に上書きしない。起動継続の可否と通知の表示タイミングは実装前に既存の起動時エラー処理と合わせる。設定保存は同じディレクトリの一時ファイルへ書き込み、フラッシュ後に`os.replace`する。書き込み失敗時は元ファイルを維持し、一時ファイルだけ後片付けする。Windowsでのファイル権限エラーもテストする。

既存のバックアップファイルと復元処理は、設定ファイルを導入しても移動・改名・削除しない。アンインストール後に利用者データ領域を残す現行方針を踏襲する。

## 3. バックアップ状態の取得と表示

`BackupService`へ管理対象一覧または読み取り専用の状態取得処理を追加し、GUIが私的メソッドやディレクトリのファイル名規則を直接参照しないようにする。対象はバックアップディレクトリ直下にある現行規則の`books_YYYYMMDD_HHMMSS.db`と、新規衝突回避規則で生成したファイルのみ。別名・途中作成ファイルは件数に含めない。

表示内容は「最後のバックアップ: YYYY/MM/DD HH:MM:SS」「管理対象: N件」「保存先: 絶対パス」。空なら「バックアップなし」「0件」。表示日時はファイル名由来であり、ファイルが存在することはDB整合性・復元可能性の保証ではない。取得時にファイルが消えた場合は再取得または明示的な読み込みエラーとし、画面を成功状態に固定しない。

手動作成は設定画面の「今すぐバックアップ」から既存の`create_backup()`を呼ぶ。実行中はボタンを無効にして二重クリックを抑制し、作成成功時は保存ファイルを知らせ状態表示を更新する。元DBがない場合（戻り値`None`）と作成失敗（例外）はそれぞれ区別して通知する。GUI操作が長時間止まる可能性は、実データ量に基づいて非同期化の要否を判断する。非同期化する場合はTkのウィジェット更新をメインスレッドに戻す。

## 4. 同じ秒に作成されたバックアップ

現行の`books_YYYYMMDD_HHMMSS.db`を既に利用しているため、初回の名前は維持する。同じ秒に作成された別ファイルは`books_YYYYMMDD_HHMMSS_001.db`、`_002.db`…と連番を付け、`O_EXCL`相当の排他作成で空いている名前を確保する。存在するファイルをSQLite接続で開いて上書きしない。確保済みの自分のファイルだけに書き込み、失敗時はそのファイルだけ削除する。

日時のパーサーとソートを両形式に対応させ、同秒では連番を昇順に扱う。自動作成の間隔判定は最新ファイルのタイムスタンプを用いる。旧形式のバックアップや移行済みバックアップは引き続き対象にする。連番枯渇時は既存ファイルを上書きせずエラーにする。多重起動時の世代整理と復元の競合については、リリース前にアプリの起動制御を確認し、必要ならディレクトリ単位の排他制御を追加する。

## 5. 作成・世代整理・復元の順序

1. 元DBの存在を確認し、他のバックアップファイルと衝突しない名前を確保する。
2. SQLite Backup APIでコピーする。失敗した場合は今回の未完成ファイルだけを消し、既存DB・既存バックアップには触れない。
3. 新規ファイルに対して整合性チェックとBook Manager用DBの検証を実施する。検証失敗でも今回のファイルだけを処理し、既存世代を削除しない。検証方式は既存の復元元検証を再利用するが、後方互換スキーマの扱いをテストで固定する。
4. 成功を確認した後だけ、管理対象ファイルから古い順に保持世代数超過分を削除する。今回の新規作成ファイルと保護対象ファイルは削除しない。保護対象が多い場合は上限件数超過を許容し、安全性を優先する。
5. 世代整理の削除に失敗した場合でも、新しく作成したバックアップは維持し、整理失敗をログとGUIへ伝える。復元前の安全バックアップが成功していれば、世代整理の失敗だけを理由に元DBを壊さない。

復元処理では復元元を事前検証し、現在DBの安全バックアップを検証まで済ませてから復元する。復元元に指定したファイルと新しい安全バックアップの両方を世代整理から守る。復元処理が失敗した場合にも安全バックアップを残す。復元時の世代整理をいつ行うかは、復元元と安全バックアップを確実に保護できる順序で実装・テストする。

設定変更直後には世代整理しない。最初のバックアップがない環境では、設定間隔に関係なく次回起動時に初回バックアップを試みる。常駐中の定期実行は行わない。手動作成成功後は、次の起動時の自動判定にその日時を反映する。

## 6. 責務と変更対象

* `config/paths.py`: バックアップ設定ファイルのパスを追加。
* 新規設定Model・Store: 値の検証、既定値、JSON読込・原子的保存、エラーの明示。
* `services/backup_service.py`: 状態の公開、一意な命名、成功確認後の整理と保護対象の扱い。
* `services/application_settings_service.py`: 設定画面からの設定参照・保存と手動作成の入口。既存APIキー処理を維持。
* `main.py`および起動処理: 保存済み設定を読み込み、`BackupService`の生成時に反映。読み込み失敗時の通知を統一。
* `gui/book_manager_application.py`: 設定表示、入力検証、手動作成、処理結果の通知。

既存の`ApplicationSettingsSnapshot`は表示値の契約を壊さず、バックアップ状態の追加または別Model導入をテストとともに決める。GUIから直接JSONファイルやバックアップファイルを操作しない。

## 7. テストと実機確認

* 設定未作成時の既定値、保存・再読込、異常入力、破損・未知スキーマ、権限エラー、失敗時の旧設定維持。
* 旧形式と新形式の一覧・最新判定、同じ秒での連続作成、既存ファイルの内容維持、途中失敗時の後片付け。
* 設定変更だけでは削除されないこと、作成失敗時に整理されないこと、保護対象があると上限を超えても残ること。
* 復元元の事前検証、復元前の安全バックアップ、復元失敗時の保護、復元元と安全バックアップの世代整理からの除外。
* GUIの空状態・成功・失敗・二重クリック対策、起動後の保存設定適用、再起動前の画面表示。
* 全pytestとWindowsソース版・配布版で確認する。別の試験用`BOOK_MANAGER_HOME`を使い、利用中の実データ・既存バックアップは試験対象にしない。更新・アンインストール・再インストール後の設定保持も確認する。

## 8. 実装前に確定する点

1. 設定ファイルの形式とパス、および破損時の起動継続・通知方法。
2. 間隔1～168時間、保持2～100件という入力範囲と、再起動後適用の画面文言。
3. 同秒連番と多重起動時の排他方式、世代整理・復元失敗時の表示方法。

この文書は実装前の設計案であり、Version 2.2の機能が既に実装済みであることを意味しない。
