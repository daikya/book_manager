## 5. 総合評価

レビュー結果は、次のとおりです。

```text
条件付き承認
```

現行のデータベース設計は、Version 0.1の初期実装を進めるための基本構成として妥当です。

特に、次の点は適切です。

* SQLiteを採用している。
* `book_items` 単一テーブルとしている。
* 主キーに `INTEGER PRIMARY KEY` を使用している。
* `title` を必須項目としている。
* ISBNと雑誌コードをTEXTで保存している。
* ISBNと雑誌コードの重複を許可している。
* 空文字をNULLへ変換する方針がある。
* 登録日時と更新日時をJSTで生成する。
* SQLiteの `CURRENT_TIMESTAMP` を使用しない。
* `title`、`isbn`、`magazine_code` にインデックスを作成する。
* 書籍名の部分一致検索に対応している。
* Version 0.1では過剰な正規化を行わない。
* 書影キャッシュをデータベースと分離している。
* SQLでプレースホルダーを使用する方針が明確である。
* Design Freeze後の変更手順が定義されている。

ただし、SQLite実装を開始する前に、いくつかの確認事項と修正事項があります。

## 6. 承認済み事項

以下の設計は、そのまま採用します。

### 6.1 SQLiteの採用

Version 0.1ではSQLiteを使用します。

ローカルの単一利用者向けデスクトップアプリとして適切です。

---

### 6.2 単一テーブル構成

Version 0.1では、`book_items` 単一テーブルを採用します。

著者、出版社、ジャンルなどは別テーブルへ分割しません。

理由は次のとおりです。

* 初期実装を小さく保てる。
* CRUD処理が単純になる。
* GUIとの対応が分かりやすい。
* 個人利用の規模では十分である。
* 実際の必要性が確認される前の過剰な正規化を避けられる。

---

### 6.3 主キー

主キーは次の定義を採用します。

```sql
id INTEGER PRIMARY KEY
```

ISBNや雑誌コードは、欠損や重複の可能性があるため主キーには使用しません。

---

### 6.4 書籍名の必須化

`title` は必須項目とします。

データベースでは `NOT NULL` を設定し、Serviceでも空文字を禁止します。

---

### 6.5 ISBNと雑誌コード

ISBNと雑誌コードはTEXTとして保存します。

理由は次のとおりです。

* ISBN-10には `X` が含まれる場合がある。
* 先頭の0を保持する必要がある。
* 数値計算の対象ではない。
* 雑誌コードにハイフンが含まれる場合がある。

---

### 6.6 重複登録

ISBNと雑誌コードにはUNIQUE制約を設定しません。

同じ書籍を複数冊所有する可能性を考慮し、重複登録を許可します。

ただし、登録時には既存データを検索し、GUIまたはServiceで警告する方針とします。

---

### 6.7 NULLと空文字

任意項目の空文字は、原則としてNULLへ変換します。

次の流れを採用します。

```text
前後の空白を除去
↓
空文字か確認
↓
空文字であればNULLへ変換
```

---

### 6.8 読了年月

読了年月はTEXT型で保存し、形式は次のとおりとします。

```text
YYYY-MM
```

Version 0.1では、読了日や再読履歴は管理しません。

---

### 6.9 登録日時と更新日時

`created_at` と `updated_at` は、Python側でJSTの日時を生成して保存します。

保存形式は次のとおりです。

```text
YYYY-MM-DD HH:MM:SS
```

SQLiteの `CURRENT_TIMESTAMP` は使用しません。

---

### 6.10 インデックス

次のインデックスを採用します。

```text
idx_book_items_title
idx_book_items_isbn
idx_book_items_magazine_code
```

Version 0.1では、著者名や出版社名にはインデックスを追加しません。

---

### 6.11 物理削除

Version 0.1では論理削除を採用しません。

削除操作では、対象レコードを物理的に削除します。

誤削除への対応は、削除確認とバックアップによって補います。

---

### 6.12 書影キャッシュ

書影画像はSQLiteへ保存せず、`cache/covers` ディレクトリへ保存します。

Version 0.1では、書影ファイルパスを `book_items` テーブルへ保存しません。

---

## 7. 条件付き承認の条件

Design Freeze前に、次の事項を反映または確定する必要があります。

### 7.1 `title` の空文字防止

現行のCREATE TABLE文では、`title TEXT NOT NULL` のみが指定されています。

SQLiteでは、空文字は `NOT NULL` 制約に違反しません。

そのため、Serviceで空文字を禁止する方針を正式に実装基準へ含めます。

Version 0.1では、データベースのCHECK制約は追加せず、Serviceで検証します。

採用方針は次のとおりです。

```text
titleをstripする
↓
空文字の場合は登録不可
↓
エラーメッセージをGUIへ返す
```

---

### 7.2 ISBNの正規化

ISBNは、保存前にハイフンと空白を除去します。

次のような入力は、同じ値として扱います。

```text
978-4-10-101001-4
9784101010014
978 4 10 101001 4
```

保存値は次の形式とします。

```text
9784101010014
```

ISBN-10の末尾に含まれる `x` は、大文字の `X` へ統一します。

---

### 7.3 ISBN不正時の扱い

ISBNの形式が不正な場合は、登録を完全には禁止しません。

理由は次のとおりです。

* 古い資料や独自資料を登録する可能性がある。
* 外部データに不完全な値が含まれる可能性がある。
* 利用者が後で修正したい場合がある。

採用方針は次のとおりです。

```text
ISBNを検証
↓
不正な場合は警告
↓
利用者が続行を選択した場合は登録可能
```

ただし、ISBNとして使用できない文字が含まれる場合は、入力内容を確認させます。

GUI仕様書で、警告表示と続行操作を定義します。

---

### 7.4 雑誌コードの正規化

雑誌コードは、前後の空白を除去します。

Version 0.1では、ハイフンの有無を自動変換しません。

外部APIまたは利用者が入力した表記を基本として保存します。

ただし、重複検索時には、将来的に正規化した比較が必要になる可能性があります。

Version 0.1では、入力値と保存値の完全一致によって検索します。

---

### 7.5 `publication_format` の選択肢

GUIのコンボボックスでは、次の初期選択肢を使用します。

```text
単行本
文庫
新書
雑誌
ムック
コミック
電子書籍
その他
```

未選択の場合はNULLとします。

Version 0.1では、データベースのCHECK制約を設定しません。

---

### 7.6 データベースVersion管理

Version 0.1から、SQLiteの `PRAGMA user_version` を使用する方針とします。

初期スキーマのVersionは次の値とします。

```text
1
```

初期化処理では、テーブルおよびインデックス作成後に、次のSQLを実行します。

```sql
PRAGMA user_version = 1;
```

起動時には、現在のスキーマVersionを確認できる構成とします。

Version 0.1の段階では複雑なマイグレーション機構は作成しませんが、将来のスキーマ変更に備えてVersion番号だけは保持します。

---

### 7.7 バックアップ実行時期

Version 0.1では、バックアップ機能を初期実装の必須機能には含めません。

ただし、次の方針を採用します。

* `backups` ディレクトリは維持する。
* SQLiteのバックアップAPIを使用する設計とする。
* 単純なファイルコピーは原則として使用しない。
* バックアップ機能の実装時期は、GUI基本機能の完成後に判断する。

データベース設計書には、将来実装予定として記載します。

---

### 7.8 書籍名部分一致検索とインデックス

`title LIKE '%検索語%'` のように先頭へワイルドカードを付ける検索では、通常のインデックスが十分に活用されない場合があります。

ただし、Version 0.1で想定するデータ件数は数百件から数千件程度であるため、現時点では問題にならないと判断します。

`idx_book_items_title` は、並び順や将来の前方一致検索にも利用できるため、そのまま採用します。

全文検索やFTSはVersion 0.1では導入しません。

## 11. 変更後の正式なスキーマ

レビュー後も、テーブル構造自体は変更しません。

```sql
CREATE TABLE IF NOT EXISTS book_items (
    id INTEGER PRIMARY KEY,
    isbn TEXT,
    magazine_code TEXT,
    title TEXT NOT NULL,
    author TEXT,
    publisher TEXT,
    publication_format TEXT,
    description TEXT,
    completion_month TEXT,
    notes TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

インデックスも変更しません。

```sql
CREATE INDEX IF NOT EXISTS idx_book_items_title
ON book_items(title);

CREATE INDEX IF NOT EXISTS idx_book_items_isbn
ON book_items(isbn);

CREATE INDEX IF NOT EXISTS idx_book_items_magazine_code
ON book_items(magazine_code);
```

初期化時に、次のスキーマVersionを設定します。

```sql
PRAGMA user_version = 1;
```

## 12. 実装時の必須事項

SQLite初期化処理とRepository実装では、次の事項を必須とします。

* データベースパスを1か所で管理する。
* `data` ディレクトリが存在しなければ作成する。
* `book_items` テーブルを `IF NOT EXISTS` で作成する。
* 必要なインデックスを `IF NOT EXISTS` で作成する。
* `PRAGMA user_version` を設定する。
* SQLにはプレースホルダーを使用する。
* `title` の空文字をServiceで拒否する。
* 任意項目の空文字をNULLへ変換する。
* ISBNを保存前に正規化する。
* 日時をPython側でJSTとして生成する。
* `created_at` は更新時に変更しない。
* `updated_at` は更新時に再生成する。
* データベース例外を握りつぶさない。
* 接続を確実に閉じる。
* 更新件数と削除件数を確認する。

## 13. 実装前テスト項目

SQLite初期化処理を実装した際は、少なくとも次の内容を確認します。

* `data` ディレクトリがない状態から作成できる。
* `book_manager.db` がない状態から作成できる。
* `book_items` テーブルが作成される。
* 3つのインデックスが作成される。
* `PRAGMA user_version` が `1` になる。

* 任意項目へNULLを保存できる。
* 同じISBNを複数登録できる。

* 日本語を正しく保存・取得できる。
* データベースファイルを開けない場合に例外が通知される。
