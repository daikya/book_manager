## 3. 使用するデータベース

Version 0.1のアプリケーションでは、SQLiteを使用します。

SQLiteを採用する主な理由は、次のとおりです。

* ローカル環境だけで動作できる。
* データベースサーバーを必要としない。
* Python標準ライブラリの `sqlite3` で利用できる。
* 単一利用者向けデスクトップアプリに適している。
* データベースを単一ファイルとして管理できる。
* 個人用の書籍管理として十分な性能がある。
* バックアップと移行が比較的容易である。

SQLiteを採用した詳細な理由は、ADRへ記録します。

## 4. データベースファイル

データベースファイル名は、次のとおりです。

```text
book_manager.db
```

開発中の保存先は、次の場所とします。

```text
book_manager/
└── data/
    └── book_manager.db
```

実装では、現在の作業ディレクトリに依存しないようにします。

プロジェクトまたはアプリケーションの基準ディレクトリから、絶対パスを生成して接続します。

配布版における保存場所は、このVersionでは確定しません。

配布方法を設計する段階で、WindowsやmacOSなどのOSごとに適切なユーザーデータ保存先を検討します。

## 5. 文字コード

SQLite内部の文字列は、UTF-8として扱います。

Python側ではUnicode文字列として扱います。

CSVや外部APIから取得したデータが別の文字コードであっても、データベースへ保存する前にPython文字列へ変換します。

## 6. データベーススキーマVersion

SQLiteのスキーマVersionは、`PRAGMA user_version` で管理します。

初期スキーマVersionは、次の値とします。

```text
1
```

テーブルとインデックスの作成が正常に完了した後、次のSQLを実行します。

```sql
PRAGMA user_version = 1;
```

アプリケーション起動時には、現在のスキーマVersionを取得できる構成にします。

Version 0.1のアプリケーションでは、複雑なマイグレーション機構は実装しません。

将来スキーマを変更する際は、現在の `user_version` を確認し、必要な移行処理を実行できるようにします。

## 11. `id`

`id` は、各レコードを一意に識別する主キーです。

```sql
id INTEGER PRIMARY KEY
```

SQLiteの `INTEGER PRIMARY KEY` によって自動採番します。

`AUTOINCREMENT` は使用しません。

削除済みIDを絶対に再利用してはならない要件がなく、通常の `INTEGER PRIMARY KEY` で十分であるためです。

ISBNや雑誌コードは、次の理由から主キーには使用しません。

* ISBNがない書籍が存在する。
* 雑誌コードがない資料が存在する。
* 同じISBNの書籍を複数冊登録する可能性がある。
* 同じ雑誌を複数登録する可能性がある。
* コードが不明な資料も登録できる必要がある。
* 電子書籍や独自資料を管理する可能性がある。

---

## 12. `isbn`

`isbn` には、ISBN-10またはISBN-13をTEXTとして保存します。

数値型は使用しません。

理由は、次のとおりです。

* ISBN-10には `X` が含まれる場合がある。
* 先頭の0を保持する必要がある。
* 計算対象ではない。
* 桁数と文字をそのまま保持する必要がある。

### 12.1 ISBNの正規化

保存前に、次の正規化を行います。

* 前後の空白を除去する。
* ISBN内の半角空白を除去する。
* ISBN内の全角空白を除去する。
* ハイフンを除去する。
* ISBN-10末尾の小文字 `x` を大文字 `X` に変換する。

例

```text
978-4-10-101001-4
```

```text
978 4 10 101001 4
```

上記は、次の値として保存します。

```text
9784101010014
```

ISBN-10の例

```text
4-10-101001-x
```

保存値

```text
410101001X
```

### 12.2 ISBNの検証

正規化後、ISBN-10またはISBN-13として形式とチェックデジットを検証します。

妥当なISBNは、そのまま保存します。

不正なISBNの場合は、利用者へ警告します。

利用者が続行を選択した場合は、不正なISBNでも登録できます。

これは、古い資料、不完全な外部データまたは後で修正する予定のデータを登録できるようにするためです。

警告後に登録する場合も、正規化処理は行います。

### 12.3 重複

ISBNには、UNIQUE制約を設定しません。

同じISBNを持つレコードの登録を許可します。

新規登録時には、同じISBNの既存レコードを検索し、該当データがある場合は警告します。

利用者が続行を選択した場合は登録できます。

## 13. `magazine_code`

`magazine_code` には、雑誌コードをTEXTとして保存します。

例

```text
12345-07
```

保存前に前後の空白を除去します。

Version 0.1では、次の処理は行いません。

* ハイフンの自動追加。
* ハイフンの自動除去。
* 桁数に基づく自動整形。
* 雑誌コードの構成要素への分割。

外部APIから取得した値または利用者が入力した値を基本として保存します。

Version 0.1の重複検索では、保存値との完全一致を使用します。

雑誌コードにもUNIQUE制約を設定しません。

同じ雑誌コードを持つレコードの登録を許可します。

---

## 14. `title`

`title` には、書籍名または雑誌名を保存します。

`title` は必須項目です。

保存前に前後の空白を除去します。

空白を除去した結果が空文字の場合は、登録または更新を許可しません。

処理は次のとおりです。

```text
titleをstripする
↓
空文字か確認する
↓
空文字の場合は検証エラーにする
↓
GUIへ具体的なエラーメッセージを返す
```

データベースでは `NOT NULL` を設定します。

空文字の禁止はServiceで実施します。

Version 0.1では、データベースのCHECK制約は追加しません。

---

## 15. `author`

`author` には、著者名を保存します。

Version 0.1では著者テーブルを作成しません。

複数の著者がいる場合は、1つの文字列として保存します。

例

```text

```

複数著者の区切り文字は、外部APIから取得した表記または利用者の入力を基本とします。

将来、著者単位の検索、集計または表記統一が必要になった場合は、著者テーブルへの分割を検討します。

出版社名の表記ゆれは、Version 0.1では完全には防止しません。

## 18. `description`

`description` には、書籍または雑誌の内容紹介を保存します。

次の情報を保存できます。

* 外部APIから取得した内容紹介。
* 利用者が手入力した説明。
* 外部情報を利用者が修正した文章。

Version 0.1では、データベース上の文字数制限を設けません。

GUIでは、複数行入力欄を使用する予定です。

---

## 19. `completion_month`

`completion_month` には、読了年月を保存します。

保存形式は、次のとおりです。

```text
YYYY-MM
```

例

```text
2026-07
```

未読、読了年月が不明または未入力の場合は、NULLとします。

Serviceでは、次の内容を検証します。

* 7文字である。
* 5文字目がハイフンである。
* 年が4桁の数字である。
* 月が2桁の数字である。
* 月が01から12までである。
* 実在する年月として扱える。

Version 0.1では読了年月を1つだけ保存します。

再読履歴を複数管理する機能は含めません。

## 20. `notes`

`notes` には、利用者が自由に入力する備考を保存します。

例

* 購入場所。
* 保管場所。
* 感想。
* 貸出状況。
* 再読予定。
* 特記事項。

Version 0.1では、備考の内容を構造化しません。

## 21. `created_at`

`created_at` には、レコードを登録した日時を保存します。

SQLiteの `CURRENT_TIMESTAMP` は使用しません。

Python側で日本標準時の日時を生成します。

保存形式は、次のとおりです。

```text
YYYY-MM-DD HH:MM:SS
```

例

```text
2026-07-17 15:30:00
```

更新時に `created_at` は変更しません。

---

## 22. `updated_at`

`updated_at` には、レコードを最後に更新した日時を保存します。

新規登録時は、`created_at` と同じ日時を保存します。

更新時は、Python側で新しい日本標準時の日時を生成します。

保存形式は、`created_at` と同じです。

## 23. NULLと空文字の扱い

任意項目に値がない場合は、NULLを保存します。

空文字は、原則として保存しません。

Serviceで次の変換を行います。

```text
文字列の前後空白を除去する
↓
空文字か確認する
↓
空文字であればNoneへ変換する
↓
SQLiteへNULLとして保存する
```

対象となるカラムは、次のとおりです。

* `isbn`
* `magazine_code`
* `author`
* `publisher`
* `publication_format`
* `description`
* `completion_month`
* `notes`

`title` は必須項目のため、NULLまたは空文字を許可しません。

## 24. 日付と日時の保存方針

SQLiteでは、日付および日時をTEXTとして保存します。

### 24.1 読了年月

```text
YYYY-MM
```

### 24.2 登録日時と更新日時

```text
YYYY-MM-DD HH:MM:SS
```

### 24.3 タイムゾーン

日時は、Python側で日本標準時として生成します。

例

```python
from datetime import datetime
from zoneinfo import ZoneInfo

JST = ZoneInfo("Asia/Tokyo")
now_jst = datetime.now(JST)
timestamp = now_jst.strftime("%Y-%m-%d %H:%M:%S")
```

SQLiteの `CURRENT_TIMESTAMP` はUTC基準になるため使用しません。

## 27. 書籍名の部分一致検索

Version 0.1では、書籍名の部分一致検索に対応します。

基本SQLは、次のとおりです。

```sql
SELECT
    id,
    isbn,
    magazine_code,
    title,
    author,
    publisher,
    publication_format,
    description,
    completion_month,
    notes,
    created_at,
    updated_at
FROM book_items
WHERE title LIKE ?
ORDER BY title ASC, id ASC;
```

Python側で検索語の前後に `%` を付けます。

例

```text
%Python%
```

検索語をSQL文字列へ直接連結しません。

必ずプレースホルダーを使用します。

`LIKE '%検索語%'` では、通常のインデックスが十分に利用されない場合があります。

ただし、Version 0.1で想定する数百件から数千件程度のデータでは、実用上の問題は小さいと判断します。

全文検索やFTSは導入しません。

## 30. データベース初期化

初回起動時または初期化処理の実行時に、次の順番で処理します。

```text
dataディレクトリの存在を確認する
↓
存在しない場合は作成する
↓
book_manager.dbへ接続する
↓
現在のPRAGMA user_versionを取得する
↓
book_itemsテーブルを作成する
↓
必要なインデックスを作成する
↓
PRAGMA user_versionを1に設定する
↓

↓

```

テーブルやインデックスがすでに存在する場合でもエラーにならないように、`IF NOT EXISTS` を使用します。

初期化処理は、複数回実行しても同じ結果になるようにします。

## 31. データベース接続方針

SQLiteへの接続処理は、複数箇所へ分散させません。

データベースパスの生成と接続処理は、専用モジュールで管理します。

基本方針は、次のとおりです。

* データベースパスを1か所で定義する。
* 必要な処理単位で接続する。
* 使用後は確実に接続を閉じる。
* コンテキストマネージャーを利用する。
* SQLへ値を直接連結しない。
* プレースホルダーを使用する。
* `sqlite3.Row` を使用してカラム名で値を参照する。
* SQLite例外を無条件に握りつぶさない。
* 書き込み処理の失敗時はロールバックする。

Version 0.1では外部キーを使用しません。

将来外部キーを導入する場合は、接続ごとに次を有効化します。

```sql
PRAGMA foreign_keys = ON;
```

## 32. INSERT方針

登録処理では、次のSQLを使用します。

```sql
INSERT INTO book_items (
    isbn,
    magazine_code,
    title,
    author,
    publisher,
    publication_format,
    description,
    completion_month,
    notes,
    created_at,
    updated_at
)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?);
```

`id` はSQLiteによる自動採番とします。

登録前に、Serviceで次の処理を行います。

* 各文字列の前後空白を除去する。
* 任意項目の空文字をNULLへ変換する。
* `title` が空でないことを確認する。
* ISBNを正規化する。
* ISBNを検証する。
* 不正なISBNの場合は警告情報を返す。
* 読了年月を検証する。
* 重複するISBNまたは雑誌コードを確認する。
* 登録日時と更新日時をJSTで生成する。

登録成功後は、新しく採番された `id` を取得します。

## 33. SELECT方針

Version 0.1では、次の取得処理を実装します。

* 全件取得。
* ID指定取得。
* 書籍名部分一致検索。
* ISBN完全一致検索。
* 雑誌コード完全一致検索。
* ISBN重複確認。
* 雑誌コード重複確認。

全件取得の基本的な並び順は、次のとおりです。

```sql
ORDER BY title ASC, id ASC
```

利用者入力を、そのまま `ORDER BY` 句へ連結しません。

GUIで並び替え機能を実装する場合は、許可したカラム名と並び順だけをRepositoryへ渡します。

## 34. UPDATE方針

更新処理は、`id` を条件として行います。

```sql
UPDATE book_items
SET
    isbn = ?,
    magazine_code = ?,
    title = ?,
    author = ?,
    publisher = ?,
    publication_format = ?,
    description = ?,
    completion_month = ?,
    notes = ?,
    updated_at = ?
WHERE id = ?;
```

更新時に `created_at` は変更しません。

更新前に、新規登録時と同じ入力検証と正規化を行います。

更新処理後は、更新件数を確認します。

更新件数が0件の場合は、対象IDが存在しないことをServiceへ通知します。

---

## 35. DELETE方針

削除処理は、`id` を条件として行います。

```sql
DELETE FROM book_items
WHERE id = ?;
```

Version 0.1では論理削除を使用しません。

対象レコードを物理的に削除します。

GUIでは、削除前に利用者へ確認を表示します。

削除後は、削除件数を確認します。

削除件数が0件の場合は、対象IDが存在しないことをServiceへ通知します。

---

## 36. トランザクション

登録、更新、削除および初期化処理では、SQLiteのトランザクションを使用します。

複数のSQLを一つの処理として実行する場合は、すべて成功した場合のみコミットします。

途中で例外が発生した場合はロールバックします。

Pythonでは、原則として接続オブジェクトのコンテキストマネージャーを使用します。

---

## 37. エラー処理

Repositoryでは、SQLite関連の例外を無条件に握りつぶしません。

想定する主なエラーは、次のとおりです。

* データベースファイルを開けない。
* ディレクトリを作成できない。
* 書き込み権限がない。
* データベースがロックされている。
* SQLに誤りがある。
* データベースが破損している。
* ディスク容量が不足している。
* 制約違反が発生した。
* 未対応のスキーマVersionである。

必要に応じて、SQLite固有の例外をアプリケーション独自例外へ変換します。

GUIには、利用者が理解できるメッセージを表示します。

内部のSQL全文や不要なシステム情報は、利用者向けメッセージへ直接表示しません。

---

## 38. データ検証

保存前に、Serviceで次の検証を行います。

* `title` が空でない。
* ISBNを正規化できる。
* ISBN-10またはISBN-13として妥当か確認する。
* 不正なISBNの場合は警告する。
* 読了年月が `YYYY-MM` 形式である。
* 月が01から12の範囲である。
* 各文字列の前後空白が除去されている。
* 任意項目の空文字がNULLへ変換されている。
* 出版形態がGUIで許可した選択肢である。
* 必要に応じて重複データを確認する。

入力検証はServiceで行い、Repositoryは保存処理に集中します。

---

## 39. ISBN不正時の登録手順

ISBNが不正な場合は、次の流れで処理します。

```text
ISBNを正規化する
↓
ISBN-10またはISBN-13として検証する
↓
不正な場合は警告結果を返す
↓
GUIが利用者へ警告を表示する
↓
利用者がキャンセルした場合は保存しない
↓
利用者が続行した場合は保存する
```

Serviceが直接確認ダイアログを表示することはありません。

Serviceは検証結果を返し、GUIが利用者との対話を担当します。

---

## 40. 重複時の登録手順

ISBNまたは雑誌コードが既存レコードと重複する場合は、次の流れで処理します。

```text
正規化済みの値で既存データを検索する
↓
重複がなければ通常登録する
↓
重複がある場合は警告結果を返す
↓
GUIが既存データを利用者へ知らせる
↓
利用者がキャンセルした場合は保存しない
↓
利用者が続行した場合は保存する
```

更新時は、更新対象自身のIDを重複判定から除外します。

---

## 41. バックアップ方針

バックアップファイルは、次のディレクトリへ保存する予定です。

```text
book_manager/
└── backups/
```

ファイル名は、次の形式を候補とします。

```text
book_manager_YYYYMMDD_HHMMSS.db
```

例

```text
book_manager_20260717_153000.db
```

Version 0.1の初期CRUD実装では、バックアップ機能を必須としません。

次の機能が完成した後に、バックアップ機能の実装時期を判断します。

* データベース初期化。
* 書籍の登録。
* 書籍の取得。
* 書籍の更新。
* 書籍の削除。
* 書籍名検索。
* 基本GUI。

バックアップを実装する場合は、SQLiteのバックアップAPIを使用します。

データベース使用中の単純なファイルコピーは、原則として使用しません。

---

## 42. 書影機能

書影画像は、SQLiteへBLOBとして保存しません。

将来書影を取得する場合は、次の場所へ保存する予定です。

```text
book_manager/
└── cache/
    └── covers/
```

Version 0.1の初期CRUDでは、書影取得および書影表示を必須機能としません。

ISBNまたは雑誌コードから外部データを取得する機能を設計する段階で、書影機能を改めて検討します。

Version 0.2のスキーマには、次のカラムを含めません。

* 書影URL。
* 書影ファイルパス。
* 書影バイナリデータ。

---

## 43. `.gitignore` 方針

実データを含むSQLiteファイル、バックアップおよびキャッシュは、原則としてGitへ登録しません。

想定する除外設定は、次のとおりです。

```gitignore
data/*.db
data/*.db-shm
data/*.db-wal

backups/*.db

cache/covers/*
```

必要な空ディレクトリを維持する場合は、`.gitkeep` を配置します。

`.gitkeep` はGitの正式な機能ではなく、空ディレクトリを管理するための慣習的なファイルです。

性能問題が発生した場合は、次の順番で確認します。

```text

↓

```

初期段階では、複雑な最適化を行いません。

## 49. セキュリティ方針

Version 0.1では、ローカルの単一利用者環境を前提とします。

データベース自体の暗号化は行いません。

次の基本対策を行います。

* SQLへ利用者入力を直接連結しない。
* プレースホルダーを使用する。
* データベースパスを利用者入力から直接生成しない。
* APIキーをデータベースへ保存しない。
* パスワードを保存しない。
* 不要な内部情報をエラーメッセージへ表示しない。
* SQLiteファイルをGitへ登録しない。
* バックアップにも同じ情報が含まれることを考慮する。

複数利用者対応や機密情報管理が必要になった場合は、セキュリティ設計を見直します。

## 50. 初期化処理のテスト項目

SQLite初期化処理では、少なくとも次の内容をテストします。

* `data` ディレクトリがない状態から作成できる。
* `book_manager.db` がない状態から作成できる。
* `book_items` テーブルが作成される。
* 3つのインデックスが作成される。
* `PRAGMA user_version` が `1` になる。
* 初期化処理を複数回実行してもエラーにならない。
* 既存データがある状態で初期化してもデータが消えない。
* 日本語を正しく保存および取得できる。
* データベースを作成できない場合に例外が通知される。

## 51. CRUDのテスト項目

## 52. 現時点の正式な設計判断

Version 0.2では、次の内容を正式に採用します。

* SQLiteを使用する。
* 開発中のデータベース保存先は `data/book_manager.db` とする。
