# データベース設計書

Version : 0.1
Last Updated : 2026-07-17

---

## 1. 目的

この文書は、`book_manager` プロジェクトで使用するSQLiteデータベースの構造、保存方針、制約、インデックス、日時管理および基本的なデータ操作方針を定義するものです。

この設計書は、SQLite初期化処理、Repository実装、Service実装およびGUI実装の基準として使用します。

Version 0.1では、必要最小限の構成を優先し、書籍情報を単一テーブルで管理します。

---

## 2. 対象範囲

この文書では、次の内容を定義します。

* 使用するデータベース。
* データベースファイルの保存場所。
* テーブル構成。
* カラム定義。
* 主キー。

* 日付と日時の保存方針。

外部APIの詳細やGUI入力仕様については、別の設計書で定義します。

## 3. 使用するデータベース

Version 0.1では、SQLiteを使用します。

SQLiteを採用する主な理由は次のとおりです。

* ローカル環境だけで動作できる。
* 別途データベースサーバーを必要としない。
* Python標準ライブラリの `sqlite3` で利用できる。
* 単一利用者向けのデスクトップアプリに適している。
* バックアップが比較的容易である。
* 小規模な書籍管理用途として十分な性能がある。

SQLite採用に関する詳細な判断理由は、今後作成するADRに記録します。

---

## 4. データベースファイル

データベースファイル名は、次のとおりとします。

```text
book_manager.db
```

保存先は、プロジェクト内の次の場所を基本とします。

```text
book_manager/
└── data/
    └── book_manager.db
```

開発時は、プロジェクト直下からの相対パスを基準として扱います。

実装では、現在の作業ディレクトリに依存せず、アプリケーションの基準ディレクトリから絶対パスを生成します。

---

## 5. 文字コード

SQLite内部では、文字列をUTF-8として扱います。

Python側でも、文字列はUnicodeとして扱います。

CSV入出力などで別の文字コードを使用する場合でも、データベースへ保存する前にPythonの文字列へ変換します。


`book_items` テーブルには、書籍、雑誌、文庫、単行本、ムックおよび電子書籍などの情報を保存します。

Version 0.1では、書籍、著者、出版社などを別テーブルへ分割しません。

### 8.1 役割

`book_items` テーブルは、利用者が所有または管理する書籍情報を保存します。

## 10. 各カラムの詳細

### 10.1 `id`

各レコードを一意に識別する主キーです。

定義は次のとおりです。

```sql
id INTEGER PRIMARY KEY
```

SQLiteのINTEGER PRIMARY KEYとして自動採番します。

Version 0.1では、外部へ公開する識別子としてUUIDなどは使用しません。

---

### 10.2 `isbn`

ISBN-10またはISBN-13を保存します。

保存時は、原則としてハイフンや空白を除去した文字列を使用します。

例

```text
9784101010014
```

ISBNは数値ではなくTEXTとして保存します。

理由は次のとおりです。

* 先頭が0になる可能性がある。
* 計算対象ではない。
* 桁数をそのまま保持する必要がある。
* ISBN-10には`X`が含まれる場合がある。

ISBNの重複は、Version 0.1ではデータベース制約で禁止しません。

同じISBNの書籍を複数冊所有する可能性があるためです。

GUIまたはServiceでは、同じISBNがすでに登録されている場合に警告を表示する方針とします。

---

### 10.3 `magazine_code`

雑誌コードをTEXTとして保存します。

例

```text
12345-07
```

保存形式は、外部サービスから取得した値または利用者が入力した値を基準とします。

Version 0.1では、雑誌コードの詳細な構造を分解して保存しません。

同じ雑誌コードの重複も、データベース制約では禁止しません。

---

### 10.4 `title`

書籍名または雑誌名を保存します。

`title` は必須項目とします。

空文字は許可しません。

GUIおよびServiceで前後の空白を除去し、結果が空文字の場合は登録エラーとします。

---

### 10.5 `author`

著者名を保存します。

Version 0.1では、著者を別テーブルへ分割しません。

複数の著者がいる場合は、外部APIの表記または利用者の入力内容に基づき、1つの文字列として保存します。

例

```text
山田太郎、鈴木花子
```

将来、著者単位の高度な検索や集計が必要になった場合は、正規化を検討します。

---

### 10.6 `publisher`

出版社名を保存します。

Version 0.1では、出版社を別テーブルへ分割しません。

同一出版社の表記ゆれについては、利用者入力または外部APIの値をそのまま保存するため、完全には防止しません。

---

### 10.7 `publication_format`

出版形態を保存します。

想定する値の例は次のとおりです。

```text
単行本
文庫
新書
雑誌
ムック
電子書籍
コミック
その他
```

GUIでは、原則としてコンボボックスから選択します。

Version 0.1では、データベースのCHECK制約は設定しません。

理由は、将来新しい区分を追加する可能性があり、GUI側の選択肢変更だけで対応できる柔軟性を残すためです。

---

### 10.8 `description`

書籍または雑誌の内容紹介を保存します。

外部APIから取得した文章または利用者の手入力内容を保存します。

文字数上限は、Version 0.1ではデータベース制約として設定しません。

GUI側では、複数行入力欄を使用する予定です。

---

### 10.9 `completion_month`

読了年月を保存します。

保存形式は次のとおりです。

```text
YYYY-MM
```

例

```text
2026-07
```

読了日ではなく読了年月のみを管理します。

未読または読了年月が不明な場合はNULLとします。

GUIでは、年月形式の検証を行います。

---

### 10.10 `notes`

利用者が自由に入力する備考を保存します。

例

* 購入場所。
* 保管場所。
* 感想。
* 貸出状況。
* 再読予定。
* 特記事項。

Version 0.1では、備考の内容を構造化しません。

---

### 10.11 `created_at`

レコードを登録した日時を保存します。

SQLiteの `CURRENT_TIMESTAMP` は使用しません。

Python側で日本標準時の日時を生成し、保存します。

保存形式は次のとおりです。

```text
YYYY-MM-DD HH:MM:SS
```

例

```text
2026-07-17 15:30:00
```

---

### 10.12 `updated_at`

レコードを最後に更新した日時を保存します。

登録時は、`created_at` と同じ値を保存します。

更新時は、Python側で新しい日本標準時の日時を生成します。

保存形式は `created_at` と同じです。

---

## 11. NULLと空文字の扱い

任意項目では、値が存在しない場合にNULLを使用します。

空文字は、原則として保存しません。

GUIまたはServiceで、次の処理を行います。

```text
前後の空白を除去
↓
空文字か確認
↓
空文字であればNULLへ変換
```

対象となる主なカラムは次のとおりです。

* `isbn`
* `magazine_code`
* `author`
* `publisher`
* `publication_format`
* `description`
* `completion_month`
* `notes`

`title` は必須項目のため、NULLまたは空文字を許可しません。

---

## 12. 日付と日時の保存方針

### 12.1 保存型

SQLiteには専用のDATE型やDATETIME型がないため、日付および日時はTEXTとして保存します。

### 12.2 読了年月

読了年月は次の形式で保存します。

```text
YYYY-MM
```

### 12.3 登録日時と更新日時

登録日時および更新日時は、次の形式で保存します。

```text
YYYY-MM-DD HH:MM:SS
```

### 12.4 タイムゾーン

登録日時および更新日時は、日本標準時で生成します。

実装では、Pythonのタイムゾーン対応日時を使用します。

例

```python
from datetime import datetime
from zoneinfo import ZoneInfo

now_jst = datetime.now(ZoneInfo("Asia/Tokyo"))
```

SQLiteの `CURRENT_TIMESTAMP` はUTC基準になるため、使用しません。

---

## 13. 主キー

主キーは `id` とします。

```sql
id INTEGER PRIMARY KEY
```

ISBNや雑誌コードは、次の理由から主キーに使用しません。

* ISBNがない書籍が存在する。
* 雑誌コードがない書籍が存在する。
* 同じISBNの書籍を複数冊登録する可能性がある。
* 手入力時にコードが不明な場合がある。
* 将来、電子書籍や独自資料を管理する可能性がある。

---

## 14. 一意制約

Version 0.1では、ISBNおよび雑誌コードにUNIQUE制約を設定しません。

重複登録は許可します。

ただし、登録時に同一コードの既存データがある場合は、ServiceまたはGUIで警告を表示する方針とします。

警告後も、利用者が必要と判断した場合は登録できるようにします。

## 15. インデックス

検索性能を考慮し、次のインデックスを作成します。

### 15.1 書籍名

```sql
CREATE INDEX IF NOT EXISTS idx_book_items_title
ON book_items(title);
```

### 15.2 ISBN

```sql
CREATE INDEX IF NOT EXISTS idx_book_items_isbn
ON book_items(isbn);
```

### 15.3 雑誌コード

```sql
CREATE INDEX IF NOT EXISTS idx_book_items_magazine_code
ON book_items(magazine_code);
```

Version 0.1では、次のカラムにはインデックスを作成しません。

* `author`
* `publisher`
* `publication_format`
* `completion_month`

将来、検索頻度やデータ件数を確認したうえで追加を検討します。

## 16. 書籍名検索

Version 0.1では、書籍名の部分一致検索に対応します。

基本的なSQLは次の形式とします。

```sql
SELECT
    id,
    isbn,
    magazine_code,
    title,
    author,
    publisher,
    publication_format,
    description,
    completion_month,
    notes,
    created_at,
    updated_at
FROM book_items
WHERE title LIKE ?
ORDER BY title ASC, id ASC;
```

検索語には、Python側で `%` を付与します。

例

```text
%Python%
```

SQL文字列へ直接検索語を連結せず、必ずプレースホルダーを使用します。

Version 0.1では、大文字小文字、全角半角、ひらがなとカタカナの同一視など、高度な表記揺れ検索には対応しません。

## 19. データベース初期化

アプリケーション起動時または初回セットアップ時に、次の処理を行います。

```text
dataディレクトリの存在確認

存在しなければ作成
```

すでにテーブルやインデックスが存在する場合でもエラーにならないように、`IF NOT EXISTS` を使用します。

## 20. データベース接続方針

SQLiteへの接続処理は、複数箇所へ分散させません。

接続先パスの生成と接続処理は、専用モジュールまたはRepository関連モジュールで管理します。

基本方針は次のとおりです。

* 必要な処理単位で接続する。
* 使用後は必ず接続を閉じる。
* `with` 文を利用する。
* 例外時は適切にロールバックする。
* SQLへ値を直接連結しない。
* `sqlite3.Row` の利用を検討する。
* 外部キーを使用する場合は、接続時に有効化する。

Version 0.1では外部キーを使用しません。

---

## 21. INSERT方針

登録処理では、主に次のカラムを指定します。

```sql
INSERT INTO book_items (
    isbn,
    magazine_code,
    title,
    author,
    publisher,
    publication_format,
    description,
    completion_month,
    notes,
    created_at,
    updated_at
)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?);
```

`id` はSQLiteによる自動採番とします。

登録前に、Serviceで次の処理を行います。

* 文字列の前後空白を除去する。
* 任意項目の空文字をNULLへ変換する。
* `title` が空でないことを確認する。
* ISBN形式を確認する。
* 読了年月形式を確認する。
* 登録日時と更新日時をJSTで生成する。

---

## 22. SELECT方針

Version 0.1では、主に次の取得処理を想定します。

* 全件取得。
* ID指定取得。
* 書籍名部分一致検索。
* ISBN指定検索。
* 雑誌コード指定検索。

全件取得では、次の並び順を基本とします。

```sql
ORDER BY title ASC, id ASC
```

GUI側で別の並び順を提供する場合は、Repositoryへ安全なソート条件を渡す設計を別途検討します。

利用者入力を、そのまま `ORDER BY` 句へ連結しません。

---

## 23. UPDATE方針

更新処理は、`id` を条件として行います。

```sql
UPDATE book_items
SET
    isbn = ?,
    magazine_code = ?,
    title = ?,
    author = ?,
    publisher = ?,
    publication_format = ?,
    description = ?,
    completion_month = ?,
    notes = ?,
    updated_at = ?
WHERE id = ?;
```

更新時に `created_at` は変更しません。

対象IDが存在しない場合は、更新件数を確認し、Serviceへ結果を返します。

---

## 24. DELETE方針

削除処理は、`id` を条件として行います。

```sql
DELETE FROM book_items
WHERE id = ?;
```

GUIでは、削除前に利用者へ確認を表示します。

Version 0.1では、論理削除用カラムは設けません。

削除したレコードは、データベースから物理的に削除します。

誤削除への対応は、バックアップで補う方針とします。

---

## 25. トランザクション

単一レコードの登録、更新、削除でも、SQLiteのトランザクション機能を使用します。

複数のSQLを一つの処理として実行する場合は、すべて成功した場合のみコミットします。

途中でエラーが発生した場合は、ロールバックします。

Pythonでは、原則として `with connection:` を使用します。

---

## 26. エラー処理

Repositoryでは、SQLite関連の例外を適切に処理します。

想定する主な例外は次のとおりです。

* データベースファイルを開けない。
* 書き込み権限がない。
* SQLに誤りがある。
* データベースが破損している。
* ロックされている。
* ディスク容量が不足している。
* 制約違反が発生した。

Repositoryで例外を無条件に握りつぶしません。

必要に応じて、アプリケーション独自の例外へ変換し、ServiceまたはGUIへ伝えます。

GUIには、利用者が理解できるメッセージを表示します。

---

## 27. データ検証

データベースへ保存する前に、Serviceで入力値を検証します。

Version 0.1で想定する主な検証は次のとおりです。

* `title` が空でない。
* ISBNがISBN-10またはISBN-13として妥当である。
* ISBNに使用できない文字が含まれていない。
* 読了年月が `YYYY-MM` 形式である。
* 読了年月の月が01から12の範囲である。
* 各文字列の前後空白が除去されている。
* 任意項目の空文字がNULLへ変換されている。

ISBNが不正な場合は、原則として警告を表示します。

完全に登録を禁止するかどうかは、GUI仕様書で最終決定します。

---

## 28. バックアップ方針

SQLiteデータベースのバックアップは、次のディレクトリへ保存する想定です。

```text
book_manager/
└── backups/
```

バックアップファイル名の候補は次の形式とします。

```text
book_manager_YYYYMMDD_HHMMSS.db
```

例

```text
book_manager_20260717_153000.db
```

Version 0.1では、次のいずれかのタイミングでバックアップする方針を検討します。

* 利用者が手動でバックアップを実行したとき。
* アプリケーション終了時。
* データベース更新前。
* 一定期間ごと。

正式なバックアップ実行仕様は、実装前に別途決定します。

データベース接続中の単純なファイルコピーは避け、SQLiteのバックアップAPIの利用を優先します。

---

## 29. キャッシュとの分離

書影などの画像キャッシュは、SQLiteデータベースへ直接保存しません。

画像ファイルは、次の場所へ保存する想定です。

```text
book_manager/
└── cache/
    └── covers/
```

Version 0.1では、書影キャッシュのファイルパスを `book_items` テーブルへ保存しません。

書影機能の実装時に、必要に応じて設計を追加します。

---

## 30. `.gitignore` 方針

実データを含むSQLiteファイルは、原則としてGitへ登録しません。

想定する除外対象は次のとおりです。

```text
data/*.db
data/*.db-shm
data/*.db-wal
backups/*.db
cache/covers/*
```

必要な空ディレクトリをGitで維持する場合は、`.gitkeep` を残します。

`.gitkeep` 自体はGitの正式な機能ではなく、空ディレクトリを管理するための慣習的なファイルです。

---

## 31. 性能方針

Version 0.1では、個人利用の書籍管理を前提とします。

数百件から数千件程度のデータを想定します。

この規模では、SQLiteと現在のインデックス構成で十分な性能が得られると考えます。

将来、件数増加により性能問題が発生した場合は、次の順番で確認します。

```text
SQLの確認
↓
インデックスの確認
↓
不要な全件取得の確認
↓
GUI側の表示件数の確認
↓
ページングの検討
↓
全文検索の検討
↓
```

## 34. スキーマ変更方針

Design Freeze後にテーブル構造を変更する場合は、次の手順を行います。

```text
変更理由を整理する
↓

↓
database_design.mdを更新する
↓
er_diagram.mdを更新する
↓
必要に応じてADRを作成する
↓
レビューする
↓
Versionを更新する
↓
移行方法を設計する
↓
```

既存利用者のデータを失う可能性がある変更は、慎重に扱います。

開発初期であっても、スキーマ変更をコードだけで行いません。

## 36. セキュリティ方針

Version 0.1では、ローカルの単一利用者環境を前提とします。

データベース自体の暗号化は行いません。

次の基本対策を行います。

* SQLへ利用者入力を直接連結しない。
* 必ずプレースホルダーを使用する。
* データベースパスを利用者入力から直接生成しない。
* APIキーをデータベースへ保存しない。
* パスワードを保存しない。
* エラーメッセージへ不要な内部情報を表示しない。
* バックアップにも同じ個人情報が含まれることを考慮する。

将来、複数利用者対応や機密情報管理が必要になった場合は、セキュリティ設計を見直します。

## 37. 実装前の確認事項

SQLite実装を開始する前に、次の事項を確認します。

* カラム構成に不足がないか。
* `title` 以外の必須項目が必要か。
* ISBNの保存形式を統一するか。
* 雑誌コードの保存形式を統一するか。
* ISBN不正時に登録を許可するか。
* `publication_format` の選択肢。
* 読了年月の入力方法。
* データベースVersion管理の要否。
* バックアップの実行タイミング。
* 書影情報をVersion 0.1へ含めるか。
* GUIで必要な並び順。
* 重複警告の具体的な条件。

これらは、レビューで確認し、必要な修正を反映します。

## 38. 現時点の設計判断

Version 0.1では、次の内容を採用します。

* SQLiteを使用する。
* データベースファイル名は `book_manager.db` とする。
* `data` ディレクトリへ保存する。
* `book_items` 単一テーブルとする。
* 主キーはINTEGER型の `id` とする。
* 書籍名 `title` を必須とする。
* ISBNと雑誌コードは任意項目とする。
* ISBNと雑誌コードの重複を許可する。
* 重複時はGUIまたはServiceで警告する。
* 空文字は原則としてNULLへ変換する。
* 読了年月は `YYYY-MM` 形式とする。
* 登録日時と更新日時はJSTで生成する。
* `CURRENT_TIMESTAMP` は使用しない。
* `title`、`isbn`、`magazine_code` にインデックスを作成する。
* 削除は物理削除とする。
* Version 0.1では正規化しない。
* 書影はSQLiteへ直接保存しない。
* SQLではプレースホルダーを使用する。

## 39. Design Freeze予定

この文書のVersion 0.1は、初回設計案です。

ER図の作成とデータベース設計レビューを行い、必要な修正を反映したVersion 0.2を、SQLite実装のDesign Freeze版とする予定です。

Version 0.2以降に設計変更する場合は、開発ガイドラインに従って、文書更新、レビューおよび必要に応じたADR作成を行います。
