## 6. 出版年月の除外

GUI設計書の入力項目一覧に、一時的に「出版年月」が記載されています。

しかし、現在の `BookItem` およびデータベース設計には出版年月フィールドが存在しません。

正式な入力項目は、次の9項目です。

```text
書籍名
ISBN
雑誌コード
著者名
出版社
出版形態
内容紹介
読了年月
備考
```

出版年月に関する記述は、注意書きとして残すのではなく、初期Versionの入力項目から完全に削除します。

理由：

* 実装者が誤って入力欄を作成することを防ぐ。
* `BookItem` とGUIの不整合を防ぐ。
* データベース変更を伴う設計変更を暗黙に発生させない。
* 初期Versionのスコープを維持する。

将来、出版年月を追加する場合は、次の順序で別途設計します。

```text
Database設計変更
↓
BookItem設計変更
↓
Repository変更
↓
BookService変更
↓
GUI変更
↓
マイグレーション設計
```

## 7. 新規登録時の選択状態

GUI設計書では、既存書籍を選択中に「新規登録」を押した場合、確認ダイアログを表示する方針です。

これは誤操作防止として妥当ですが、初期Versionでは次の操作体系のほうが分かりやすくなります。

```text
一覧選択中
↓
入力内容を変更
↓
更新ボタンで既存データを更新
```

新しい書籍を登録する場合：

```text
入力クリア
↓
新規登録
```

ただし、新規登録ボタンを禁止する必要はありません。

設計方針は次で確定します。

* 選択中でも新規登録ボタンは使用可能。
* 選択中の場合は確認ダイアログを表示する。
* 確認後に登録した場合、既存データは変更しない。
* 新しく登録されたデータへ選択を移す。

この仕様を明確に記載します。

## 8. 更新時の重複確認順序

更新時には、次の順序で処理する必要があります。

```text
編集対象IDを確認
↓
フォーム入力値を取得
↓
重複候補を検索
↓
自分自身のIDを候補から除外
↓
候補が残る場合は重複確認
↓
更新確認
↓
更新用BookItemを生成
↓
service.update_book()を呼び出す
```

重複確認と通常の更新確認の順序を明確にします。

推奨順序は、重複確認を先に行い、最後に更新確認を行う方式です。

理由：

* 重複候補を確認した後で最終的な更新意思を確認できる。
* 更新確認後に追加の確認が出る不自然さを避けられる。
* 処理の最終段階で更新確認を行える。

ただし、確認ダイアログが2回続く可能性があります。

初期Versionでは許容します。

## 9. 予期しない例外

GUI設計書では、予期しない例外について、一般的なメッセージを利用者へ表示する方針になっています。

実装では、例外を握りつぶさないよう、次の処理を行います。

```python
except Exception:
    traceback.print_exc()
    messagebox.showerror(
        "処理エラー",
        "処理中にエラーが発生しました。",
    )
```

初期Versionではログファイルを導入しません。

標準エラーへトレースバックを出力することで、開発時の調査を可能にします。

本番利用時のログ保存は、将来の設計対象とします。

## 10. GUIテスト範囲

GUI設計書では、GUIクラスの生成、一覧表示、フォーム反映などを自動テスト対象としています。

方向性は妥当です。

ただし、Tkinterのテストは実行環境に依存しやすいため、初期Versionでは次の範囲に絞ります。

自動テスト対象：

```text
GUIクラスを生成できる
初期の選択IDがNone
BookItemをフォームへ反映できる
フォームをクリアできる
一覧を再描画できる
Noneを空文字列として表示できる
更新用BookItemを生成できる
```

手動テスト対象：

```text
各ボタンの操作
ダイアログの表示
検索入力欄でのEnter操作
TreeView選択
スクロール
フォーカス移動
Windowsでの表示
macOSでの表示
```

登録、検索、更新、削除の業務ロジックは、すでにServiceテストで確認されています。

GUIテストで同じロジックを過剰に再検証しません。

## 11. GUIテスト実行環境

Tkinterの自動テストには、画面表示環境が必要になる場合があります。

特に次の環境では注意が必要です。

```text
GUIを利用できないCI環境
ディスプレイのないLinux環境
Tkが正しく導入されていないPython環境
macOSのPython配布元によるTk差異
```

初期Versionでは、開発端末上で次の形式を使用します。

```python
root = tk.Tk()
root.withdraw()
```

テスト終了時には必ず次を実行します。

```python
root.destroy()
```

Tkを生成できない環境での自動テスト対応は、初期Versionの対象外とします。

# アーキテクチャレビュー

## 12. 依存方向

GUI設計では、次の依存方向が維持されています。

```text
BookManagerApplication
↓
BookService
↓
BookRepository
↓
SQLite
```

GUIからRepositoryやSQLiteへの直接アクセスはありません。

適切です。

---

## 13. GUIとServiceの責務分担

GUIの責務：

```text
入力値を取得する
入力値を表示する
BookServiceを呼び出す
結果を一覧へ表示する
ダイアログを表示する
選択状態を管理する
```

Serviceの責務：

```text
入力値を正規化する
入力値を検証する
日時を設定する
BookItemを生成する
Repositoryを呼び出す
重複候補を統合する
created_atを保持する
updated_atを更新する
```

責務分担は明確です。

---

## 14. GUIからValidatorを呼ばない方針

GUIがValidatorを直接呼び出さない方針は適切です。

GUIからValidatorを呼び出すと、次の問題が発生します。

* ServiceとGUIで検証順序が重複する。
* 正規化前の値をValidatorへ渡す可能性がある。
* エラー処理が分散する。
* Serviceを経由しない経路が生まれる。
* 将来の仕様変更箇所が増える。

ValidatorはService経由でのみ使用します。

---

## 15. GUIで正規化しない方針

GUIは、入力された文字列を原則としてそのままServiceへ渡します。

適切です。

ただし、`Text` ウィジェットから値を取得する際は、末尾にTkinterが自動付加する改行を含めないため、次の形式を使用します。

```python
text_widget.get(
    "1.0",
    "end-1c",
)
```

これは業務上の正規化ではなく、Tkinter固有の取得方法です。

---

## 16. 依存性注入

`BookManagerApplication` が、ルートウィンドウと `BookService` を受け取る設計は適切です。

```python
def __init__(
    self,
    root: tk.Tk,
    service: BookService,
) -> None:
```

利点：

* GUIがService生成方法を知らなくてよい。
* 一時データベースを使ったテストができる。
* GUI単体の生成が容易になる。
* 起動処理と画面処理を分離できる。

# 登録フローレビュー

## 43. 登録処理

登録処理の流れは適切です。

```text
入力値を取得
↓
重複候補を確認
↓
必要に応じて利用者へ確認
↓
service.add_book()
↓
一覧再読み込み
↓
登録した書籍を選択
```

---

## 44. 重複候補確認

登録前に次を呼び出す設計は、Service設計と一致しています。

```python
service.find_duplicate_candidates(
    isbn=isbn,
    magazine_code=magazine_code,
)
```

重複を自動的に拒否しない方針も適切です。

---

## 45. 重複候補ダイアログ

候補を最大5件表示する設計は妥当です。

候補数が多い場合に、ダイアログが過度に大きくなることを防げます。

表示項目は、最低限次を含めます。

```text
ID
書籍名
```

可能であれば、ISBNまたは雑誌コードも含めると識別しやすくなりますが、初期Versionでは必須としません。

---

## 46. 登録成功後

登録成功後に一覧を再読み込みし、登録したIDを選択する設計は適切です。

フォームにも保存後の正規化済み値を表示できます。

---

## 47. 登録成功ダイアログ

登録のたびに成功ダイアログを表示する仕様は、初期Versionでは許容します。

ただし、連続登録時に操作回数が増える可能性があります。

将来、ステータスバーだけの通知へ変更することを検討できます。

初期Versionでは設計どおり情報ダイアログを使用します。

## 49. 更新用BookItem

GUIが更新用 `BookItem` を生成し、Serviceへ渡す設計は、現在のService APIと一致しています。

GUIでは、次を設定しません。

```text
created_at
updated_at
```

Serviceが既存データと現在日時から設定します。

---

## 50. 更新時の重複候補

自分自身のIDを候補から除外する方針は必須です。

除外しなければ、ISBNや雑誌コードを変更していない更新でも、常に自分自身が重複候補として表示されます。

処理例：

```python
candidates = [
    candidate
    for candidate in candidates
    if candidate.id != self._selected_book_id
]
```

---

## 51. 更新後の選択

更新成功後に一覧を再読み込みし、同じIDを再選択する方針は適切です。

利用者が更新結果を確認しやすくなります。

---

## 52. 更新対象消失

`service.update_book()` が `False` を返した場合に、一覧を再読み込みしてフォームをクリアする方針は適切です。

別プロセスで対象が削除された場合にも対応できます。

## 61. イベント引数

ボタンの `command` から呼ぶメソッドは、原則として引数なしとします。

イベントバインドから呼ぶメソッドは、イベント引数を受け取ります。

例：

```python
def _on_search(
    self,
    event: tk.Event | None = None,
) -> None:
```

この形にすると、ボタンとEnterキーの両方から同じ処理を呼べます。

ただし、型ヒントの詳細は実装時にTkinterの型定義へ合わせます。
