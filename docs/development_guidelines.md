# 開発ガイドライン

Version : 0.1
Last Updated : 2026-07-17

---

## 1. 目的

この文書は、`book_manager` プロジェクトにおける開発方針、設計手順、Git運用、ドキュメント管理、実装およびテストの基本ルールを定めるものです。

開発中の判断に迷った場合は、この文書を基準とします。

このガイドラインは、プロジェクトの進行に応じて見直します。ただし、内容を変更する場合は、変更理由を明確にし、関連する設計や運用への影響を確認します。

---

## 2. 基本方針

このプロジェクトでは、次の方針を重視します。

* 小さく完成させる。
* シンプルな設計を優先する。
* 実装前に設計する。
* ドキュメントを正式な成果物として扱う。
* 保守しやすいコードを書く。
* 将来の変更が容易な構成を目指す。
* 必要以上に複雑な仕組みを導入しない。
* 一つの変更を小さな単位で管理する。
* 設計と実装の整合性を維持する。
* 動作確認を行った状態で変更を確定する。

---

## 3. 小さく完成させる

最初からすべての機能を実装しようとせず、必要最小限の機能から完成させます。

Version 0.1では、書籍管理アプリとして最低限必要な機能を優先します。

機能を追加する場合は、次の点を確認します。

* 現在のVersionに本当に必要か。
* 後のVersionへ延期できないか。
* 既存の設計を不必要に複雑にしないか。
* 保守やテストの負担が大きくなりすぎないか。
* 利用者にとって明確な価値があるか。

将来必要になる可能性だけを理由として、機能や仕組みを先に作りません。

---

## 4. シンプルな設計を優先する

同じ目的を達成できる場合は、理解しやすく、変更しやすい設計を選びます。

次のような過剰設計は避けます。

* 現時点で不要な抽象化。
* 利用予定が決まっていない拡張機構。
* 不要なクラス分割。
* 不要なデザインパターン。
* 不要な外部ライブラリ。
* 不要な非同期処理。
* 不要な設定ファイル。
* 実際には使われない汎用機能。

ただし、単純化によって責務が不明確になったり、変更が困難になったりする場合は、適切に分割します。

---

## 5. ドキュメント駆動開発

このプロジェクトでは、Documentation-Driven Developmentを採用します。

開発は、原則として次の順番で進めます。

```text
要件を整理する
↓
設計文書を作成または更新する
↓
レビューする
↓
必要な修正を行う
↓
設計を承認する
↓
Design Freezeする
↓
実装する
↓
テストする
↓
実装結果を文書へ反映する
```

設計が確定していない状態で、実装だけを先に進めません。

ドキュメントは、実装の補助資料ではなく、ソースコードと同様に管理する正式な成果物です。

## 6. ドキュメント管理

### 6.1 ドキュメントの保存場所

設計文書、開発ルール、テスト計画、ADRおよびリリースノートは、原則として `docs` ディレクトリ配下に保存します。

### 6.2 Versionと更新日

主要な文書には、Versionと最終更新日を記載します。

例

```text
Version : 0.2
Last Updated : 2026-07-17
```

### 6.3 実装との整合性

設計書と実装内容は、常に可能な限り一致させます。

実装を変更した場合は、関連する文書への影響を確認します。

設計書に記載されていない仕様を、実装だけに追加しません。

### 6.4 重複文書の禁止

同じ内容を複数の文書へ重複して記載しないようにします。

複数の文書から参照する必要がある場合は、正式な記載先を一つに決め、他の文書から参照します。

### 6.5 不要文書の整理

古い構成の文書、役割が重複する文書、内容が無効になった文書は、そのまま残しません。

必要に応じて次のいずれかを行います。

* 更新する。
* 統合する。
* 移動する。
* 改名する。
* 削除する。

不要な文書を残して、現在有効な仕様が分からなくなる状態を避けます。

## 7. Design Freeze

レビューと承認が完了した設計は、実装基準としてDesign Freezeします。

Design Freezeは、設計を永久に変更できないという意味ではありません。

設計変更が必要になった場合は、次の手順を行います。

```text
変更理由を整理する
↓
影響範囲を確認する
↓
関連文書を更新する
↓
必要に応じてADRを作成する
↓
レビューする
↓
Versionを更新する
↓
承認する
↓
実装へ反映する
↓
テストする
```

Design Freeze後に、設計書を更新せずコードだけを変更しません。

データベース設計については、Version 0.2を最初のSQLite実装基準とする予定です。

---

## 8. 実装中の設計変更

実装中に設計変更の必要性に気付いた場合は、思いついた内容をそのままコードへ反映しません。

原則として次の順番で対応します。

```text
設計上の問題を記録する
↓
変更案を検討する
↓
設計書を更新する
↓
必要に応じてADRを作成する
↓
レビューする
↓
承認する
↓
実装する
```

ただし、次のような軽微な修正は、必ずしもADRを必要としません。

* 誤字修正。
* コメント修正。
* 動作に影響しない命名修正。
* 軽微な画面配置調整。
* 設計変更を伴わないバグ修正。

設計変更に該当するか判断が難しい場合は、影響範囲が将来まで残るかを基準に判断します。

## 9. ADR運用

ADRは、Architecture Decision Recordの略称です。

重要な設計判断について、採用理由、比較した案および影響を記録します。

### 9.1 ADRを作成する対象

原則として、次の判断ではADRを作成します。

* データベースの選定。
* GUIライブラリの選定。
* アプリケーション構成の選定。
* レイヤー構成の変更。
* データモデルの大きな変更。
* 外部APIや外部サービスの選定。
* 日付や日時の保存方式。
* エラー処理の基本方針。
* 将来の機能追加へ影響する技術選定。
* 既存のDesign Freezeを変更する判断。

### 9.2 ADRを作成しない対象

原則として、次の変更ではADRを作成しません。

* 誤字や脱字の修正。
* 軽微な画面配置の変更。
* 既存設計に沿ったバグ修正。
* 変数名や関数名の軽微な変更。
* コメントの修正。
* ドキュメントの表現調整。
* 動作に影響しないコード整理。

### 9.3 ADRの状態

ADRには、必要に応じて次の状態を記載します。

* Proposed：提案中。
* Accepted：採用済み。
* Rejected：不採用。
* Superseded：別のADRに置き換えられた。
* Deprecated：非推奨。

一度採用したADRを変更する場合は、内容を直接書き換えて判断履歴を消すのではなく、新しいADRで置き換えることを基本とします。

## 10. アーキテクチャ方針

Version 0.1では、次のレイヤー構成を基本案とします。

```text
GUI
↓
Service
↓
Repository
↓
SQLite
```

各レイヤーの責務は、次のとおりです。

### GUI

* 画面表示。
* 入力受付。
* 利用者操作の受付。
* 入力エラーの表示。
* Serviceの呼び出し。

### Service

* アプリケーション固有の処理。
* 入力値の検証。
* データ変換。
* 複数のRepository操作の調整。
* GUIとRepositoryの橋渡し。

### Repository

* SQLiteへの登録。
* SQLiteからの取得。
* 更新処理。
* 削除処理。
* SQLの管理。
* データベース例外の整理。

### SQLite

* 書籍情報の永続保存。
* 制約によるデータ整合性の維持。
* インデックスによる検索支援。

詳細は、今後作成する `docs/architecture/architecture.md` で定義します。

## 11. コーディング方針

### 11.1 読みやすさを優先する

短さよりも、意図が理解しやすいコードを優先します。

過度に短い変数名や、複雑な一行処理を避けます。

### 11.2 一つの関数に一つの責務

一つの関数やメソッドには、可能な限り一つの責務を持たせます。

入力検証、データベース処理、画面表示などを、一つの関数へ詰め込みません。

### 11.3 命名

変数名、関数名、クラス名およびファイル名は、その役割が分かる名前にします。

一般的なPythonの命名規則に従います。

* クラス名：PascalCase。
* 関数名：snake_case。
* 変数名：snake_case。
* 定数名：UPPER_SNAKE_CASE。
* モジュール名：snake_case。

### 11.4 型ヒント

可能な範囲で型ヒントを使用します。

型ヒントは、コードの理解、補完および保守性の向上を目的とします。

### 11.5 コメント

コードを読めば明らかな内容を、そのまま説明するコメントは避けます。

コメントには、主に次の内容を記載します。

* なぜその処理が必要なのか。
* なぜ別の方法を採用しなかったのか。
* 外部仕様による制約。
* 誤解しやすい処理の意図。
* 将来変更する際の注意点。

### 11.6 マジックナンバー

意味が分からない数値や文字列を、コードへ直接埋め込まないようにします。

必要に応じて定数として定義します。

### 11.7 例外処理

例外を無条件に握りつぶしません。

次のような処理は避けます。

```python
try:
    ...
except Exception:
    pass
```

例外を捕捉する場合は、対象を可能な限り限定し、利用者への表示、ログ記録または上位処理への再送出を行います。

### 11.8 外部ライブラリ

標準ライブラリで十分に実現できる場合は、不要な外部ライブラリを導入しません。

外部ライブラリを追加する場合は、次の点を確認します。

* 利用目的。
* 保守状況。
* ライセンス。
* 対応OS。
* Pythonの対応Version。
* 将来の更新負担。
* 標準ライブラリで代替できない理由。

重要な技術選定に該当する場合は、ADRを作成します。

## 12. データベース実装方針

Version 0.1ではSQLiteを使用します。

データベース実装では、次の方針を守ります。

* SQLをGUIへ直接記述しない。
* SQLはRepositoryで管理する。
* データベース接続処理を分散させない。
* プレースホルダーを使用する。
* 文字列連結でSQLを組み立てない。
* 空文字を必要に応じてNULLへ変換する。
* 日付と日時の保存形式を統一する。
* CURRENT_TIMESTAMPへ依存しない。
* JSTで日時を生成する。
* トランザクションの範囲を明確にする。
* エラー時は必要に応じてロールバックする。
* スキーマ変更時は設計書を先に更新する。

詳細は、今後作成するデータベース設計書で定義します。

---

## 13. GUI実装方針

GUIは、利用者が操作を迷わないことを優先します。

次の方針を基本とします。

* 入力項目の意味を明確にする。
* 必須項目を分かりやすくする。
* エラー内容を具体的に表示する。
* 保存前に入力値を検証する。
* 削除前に確認する。
* 処理成功時に必要な結果を表示する。
* データ未登録時にも画面が崩れないようにする。
* 長い処理中に画面が無反応にならないよう配慮する。
* キーボード操作にも配慮する。
* 画面とデータベース処理を直接結合しない。

画面の項目や遷移は、今後作成する画面仕様書で定義します。

## 14. テスト方針

実装した機能は、正常系だけでなく、異常系および境界値も確認します。

### 14.1 主な確認対象

* 正常な登録。
* 正常な更新。
* 正常な削除。
* 部分一致検索。
* データが存在しない場合。
* 必須項目が空の場合。
* 不正なISBN。
* 不正な日付。
* 長い文字列。
* 重複データ。
* SQLiteファイルが存在しない場合。
* SQLiteへ接続できない場合。
* 外部APIが利用できない場合。
* 外部APIから不完全なデータが返された場合。

### 14.2 テストの実行

変更内容に応じて、関連するテストを実行します。

コミット前には、少なくとも変更した機能に関係する動作確認を行います。

自動テストを追加できる処理は、可能な範囲で自動化します。

GUI操作など、自動化が難しい項目は、確認手順を文書化します。

### 14.3 不具合修正

不具合を修正する場合は、可能な限り次の手順で対応します。

```text
不具合を再現する
↓
原因を特定する
↓
再現テストを作成する
↓
修正する
↓
テストが成功することを確認する
↓
関連機能への影響を確認する
```

## 15. Git運用

### 15.1 基本ルール

Gitでは、次のルールを守ります。

* 1コミットを1つの目的にする。
* 無関係な変更を一つのコミットへ混在させない。
* レビューしやすい単位でコミットする。
* 変更内容が分かるコミットメッセージを書く。
* コミット前に `git status` を確認する。
* 必要に応じて差分を確認する。
* 動作確認後にコミットする。
* コミット後は必要に応じて `git push` を行う。
* 不要な生成物や一時ファイルをコミットしない。
* パスワードやAPIキーをコミットしない。

### 15.2 コミットメッセージ形式

コミットメッセージは、次の形式とします。

```text
<英語のプレフィックス>: <日本語の説明>
```

説明文は常体で記述します。

例

```text
docs: 開発ガイドラインを追加
feat: 書籍登録機能を追加
fix: ISBN検証時の例外を修正
refactor: データベース接続処理を分離
test: Repositoryの単体テストを追加
chore: プロジェクト初期構成を整理
```

### 15.3 プレフィックス

| プレフィックス    | 用途              |
| ---------- | --------------- |
| `feat`     | 新しい機能の追加        |
| `fix`      | 不具合の修正          |
| `docs`     | ドキュメントの追加・変更    |
| `refactor` | 動作を変えないコード構造の改善 |
| `test`     | テストの追加・変更       |
| `chore`    | 設定、環境、構成整理、保守作業 |
| `style`    | コードの意味を変えない書式修正 |
| `perf`     | 性能改善            |
| `build`    | ビルドや依存関係の変更     |
| `ci`       | CI設定の変更         |
| `revert`   | 以前の変更の取り消し      |

無理に細かいプレフィックスを使い分ける必要はありません。

用途が明確でない場合は、変更の主目的を基準に選びます。

### 15.4 ドキュメントのコミット

原則として、ドキュメントが一つ完成するごとにコミットします。

例

```text
docs: docsディレクトリのREADMEを追加
docs: 開発ガイドラインを追加
docs: データベース設計書を追加
docs: ER図を追加
docs: データベース設計レビューを追加
docs: SQLite採用理由のADRを追加
```

### 15.5 コミット前の確認

コミット前に、原則として次のコマンドを使用します。

```powershell
git status
git diff
```

新規ファイルをステージへ追加した後は、必要に応じて次のコマンドで確認します。

```powershell
git diff --staged
```

問題がなければ、コミットしてpushします。

```powershell
git add <対象>
git commit -m "<コミットメッセージ>"
git push
```

削除を含む変更では、必要に応じて次を使用します。

```powershell
git add -A
```

## 16. ファイルとディレクトリの管理

### 16.1 空ディレクトリ

Gitは空ディレクトリを管理しないため、必要な空ディレクトリには `.gitkeep` を配置します。

ただし、将来使う可能性だけを理由として、不要なディレクトリを増やしません。

### 16.2 一時ファイル

次のようなファイルは、原則としてGitへ登録しません。

* Pythonのキャッシュ。
* ローカルのSQLiteデータベース。
* 書影キャッシュ。
* バックアップファイル。
* ログファイル。
* IDE固有の一時ファイル。
* OSが生成する管理ファイル。
* APIキーや認証情報。
* 個人環境固有の設定。

対象は `.gitignore` で管理します。

### 16.3 エクスプローラーでの削除

Git管理中のファイルやディレクトリを、エクスプローラーから削除しても問題ありません。

削除後は、次のコマンドで変更内容を確認します。

```powershell
git status
```

削除をGitへ反映する場合は、次のように操作します。

```powershell
git add -A
git commit -m "<コミットメッセージ>"
git push
```

削除対象に必要なファイルが含まれていないことを、コミット前に確認します。

## 17. レビュー方針

重要な文書や設計は、実装前にレビューします。

レビューでは、主に次の点を確認します。

* 要件を満たしているか。
* 内容に矛盾がないか。
* 不要に複雑ではないか。
* 責務が明確か。
* 将来の変更が困難にならないか。
* データの整合性を保てるか。
* エラー時の動作が定義されているか。
* テスト可能な設計か。
* 他の文書と整合しているか。
* 実装基準として十分に具体的か。

レビュー結果は、必要に応じて次のように分類します。

* 承認。
* 条件付き承認。
* 要修正。
* 再設計。

条件付き承認の場合は、条件を満たしたことを確認してからDesign Freezeします。

---

## 18. Version管理

Versionは、変更の規模と開発段階に応じて更新します。

開発初期は、次のようなVersionを使用します。

```text
0.1
0.2
0.3
```

Version 1.0は、最初の正式版として必要な機能が完成し、動作確認と文書整備が完了した段階とします。

文書のVersionとアプリケーションのVersionは、必ずしも同一である必要はありません。

ただし、どの設計Versionを基準として実装したか分かるようにします。

## 19. 完了の定義

機能または文書は、作成しただけでは完了としません。

### 19.1 ドキュメントの完了条件

* 目的が明確である。
* 必要な項目が記載されている。
* 他の文書と矛盾していない。
* 誤字や表記ゆれを確認している。
* レビューが完了している。
* 必要な修正が反映されている。
* Gitへコミットされている。
* 必要に応じてGitHubへpushされている。

### 19.2 実装の完了条件

* 設計書に基づいて実装されている。
* 正常系が動作する。
* 想定する異常系が処理される。
* 関連テストが成功する。
* 不要なデバッグコードが残っていない。
* ドキュメントと実装が一致している。
* Gitへコミットされている。
* 必要に応じてGitHubへpushされている。

## 21. ガイドラインの変更

このガイドライン自体も、必要に応じて変更できます。

変更する場合は、次の点を確認します。

* 変更が必要な理由。
* 現在の開発手順への影響。
* 既存ドキュメントへの影響。
* Git運用への影響。
* 実装済みコードへの影響。
* 過去の判断との整合性。

軽微な表現修正を除き、重要な方針変更はレビューしてから適用します。
