# 利用者データ保存先・既存データ移行設計書

Version : 1.0
Last Updated : 2026-09-08
Status : Design Draft

---

## 1. 目的

本設計書は、book_manager Version 2.0で実施する利用者データ保存先の一元化と、Version 1.9以前の保存先からの既存データ移行について定義する。

Version 2.0では、Pythonを導入していないWindows環境へアプリケーションを配布できるようにする。その前提として、データベース、バックアップおよび表紙画像キャッシュを、ソースコードやアプリケーションのインストール先から分離する。

また、現在利用している`data/books.db`を失わず、新しい保存先へ安全に引き継げるようにする。

本設計は、次の実装における正式な基準とする。

* 利用者データ保存先の決定
* 保存先ディレクトリの作成
* 既存データベースの検出と移行
* 既存バックアップの引き継ぎ
* 既存表紙画像キャッシュの引き継ぎ
* 表紙画像パスの互換処理
* 起動処理への組み込み
* 移行結果とエラーの通知
* 自動テストとWindows実環境での確認

---

## 2. 背景

### 2.1 現在の保存先

Version 1.9の`main.py`では、次の相対パスを直接指定している。

```text
data/books.db
backups/
cache/covers/
```

この相対パスは、アプリケーションを起動したときのカレントディレクトリを基準に解決される。

### 2.2 `paths.py`との不一致

`src/book_manager/config/paths.py`には、次の定義が存在する。

```text
PROJECT_ROOT
DATA_DIR
BACKUP_DIR
CACHE_DIR
DATABASE_PATH = DATA_DIR / "book_manager.db"
```

一方、現在の正式な起動処理である`main.py`はこれらを使用せず、データベース名として`books.db`を使用している。

したがって、次の不一致がある。

| 項目 | `paths.py` | `main.py` |
| --- | --- | --- |
| 基準位置 | リポジトリルート | カレントディレクトリ |
| データベース名 | `book_manager.db` | `books.db` |
| バックアップ先 | `BACKUP_DIR` | `Path("backups")` |
| キャッシュ先 | `CACHE_DIR` | `Path("cache/covers")` |

### 2.3 配布版で生じる問題

この状態で実行ファイル化すると、次の問題が生じる可能性がある。

* 起動方法によって異なるデータベースを参照する。
* インストール先への書き込み権限が不足する。
* アプリケーション更新時に利用者データを上書きまたは消失する。
* アンインストール時に利用者データも削除される。
* ショートカットから起動した場合に保存先が変わる。
* ソース版と配布版で異なるデータを参照する。

Version 2.0では、これらを保存先の一元化と既存データ移行によって解消する。

## 3. 対象範囲

### 3.1 対象

本設計の対象は次のとおりとする。

* SQLiteデータベース`books.db`
* 自動バックアップおよび手動復元に使用するバックアップファイル
* 表紙画像キャッシュ
* 保存先を決定する設定処理
* 保存先の初期化処理
* Version 1.9以前からの移行処理
* `main.py`の依存関係組み立て
* 移行に関する起動時通知

### 3.2 対象外

次は本設計の対象外とする。

* SQLiteテーブル構造の変更
* 書籍情報や読書履歴の仕様変更
* バックアップファイル形式の変更
* 表紙画像の自動削除
* 設定画面からの保存先変更
* 複数の利用者データ領域の切り替え
* クラウド同期
* macOSおよびLinux向け保存先
* インストーラーそのものの詳細仕様
* アプリケーション内からの自動更新

## 4. 基本方針

利用者データ保存先と移行処理には、次の方針を適用する。

* アプリケーション本体と利用者データを分離する。
* Windowsの利用者単位のローカルアプリケーションデータ領域を使用する。
* 保存先をカレントディレクトリへ依存させない。
* ソース版と配布版で同じ既定保存先を使用する。
* 保存先の決定を`config/paths.py`へ集約する。
* RepositoryおよびServiceには、これまでどおり`Path`を注入する。
* 既存データは移動ではなく複製する。
* 元データは自動削除しない。
* 移行先に既存データがある場合は上書きしない。
* 移行処理は再実行しても安全な冪等処理とする。
* SQLiteデータベースはSQLite Backup APIで複製する。
* 部分的な移行結果を正式データとして扱わない。
* 移行失敗時も、可能な限りアプリケーションを安全に起動する。
* テスト時は実利用者データへアクセスしない。

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| 利用者データルート | Version 2.0以降のデータを保存する最上位ディレクトリ |
| 新保存先 | `%LOCALAPPDATA%\book_manager`配下の保存先 |
| 旧保存先 | Version 1.9以前に使用していたプロジェクト直下の相対保存先 |
| 旧データベース | 原則として`<旧ルート>\data\books.db` |
| 移行 | 旧保存先のデータを新保存先へ安全に複製する処理 |
| 移行元 | 旧保存先 |
| 移行先 | 新保存先 |
| 配布版 | PyInstallerとインストーラーによって導入されたアプリケーション |
| ソース版 | 開発環境で`python main.py`により起動するアプリケーション |

## 6. 新しい保存先

### 6.1 利用者データルート

Windowsでは、環境変数`LOCALAPPDATA`が示すディレクトリの配下に`book_manager`を作成する。

```text
%LOCALAPPDATA%\book_manager\
```

一般的な実体は次のようになる。

```text
C:\Users\<利用者名>\AppData\Local\book_manager\
```

### 6.2 ディレクトリ構成

```text
%LOCALAPPDATA%\book_manager\
├── data\
│   └── books.db
├── backups\
│   └── books_YYYYMMDD_HHMMSS.db
└── cache\
    └── covers\
        └── <URLのSHA-256値>.<拡張子>
```

### 6.3 正式なパス

| 用途 | パス |
| --- | --- |
| 利用者データルート | `%LOCALAPPDATA%\book_manager` |
| データディレクトリ | `%LOCALAPPDATA%\book_manager\data` |
| データベース | `%LOCALAPPDATA%\book_manager\data\books.db` |
| バックアップ | `%LOCALAPPDATA%\book_manager\backups` |
| キャッシュ | `%LOCALAPPDATA%\book_manager\cache` |
| 表紙画像 | `%LOCALAPPDATA%\book_manager\cache\covers` |

データベース名は、現在の正式な実データで使用している`books.db`へ統一する。`book_manager.db`は新しい正式名称として採用しない。

### 6.4 環境変数による上書き

開発、テストおよび障害調査のため、環境変数`BOOK_MANAGER_HOME`による利用者データルートの上書きを可能にする。

```text
BOOK_MANAGER_HOME=C:\temporary\book_manager_test
```

優先順位は次のとおりとする。

1. 呼び出し側から明示された利用者データルート
2. 環境変数`BOOK_MANAGER_HOME`
3. 環境変数`LOCALAPPDATA`配下の`book_manager`

`BOOK_MANAGER_HOME`が空文字または空白だけの場合は、未指定として扱う。

### 6.5 `LOCALAPPDATA`を取得できない場合

Windowsで`LOCALAPPDATA`が未設定または空の場合は、誤った場所へ新規データベースを作成せず、保存先を決定できないことを示す例外を発生させる。

この例外は起動処理で捕捉し、利用者へ次の趣旨を通知して終了する。

```text
利用者データの保存先を取得できないため、アプリケーションを起動できませんでした。
```

カレントディレクトリへ暗黙にフォールバックしない。

## 7. パス設定の設計

### 7.1 配置先

```text
src/book_manager/config/paths.py
```

### 7.2 データ構造

関連するパスを個別のモジュール定数として保持するのではなく、不変のデータクラスへまとめる。

想定する構造は次のとおりとする。

```python
@dataclass(frozen=True, slots=True)
class ApplicationPaths:
    root_directory: Path
    data_directory: Path
    database_path: Path
    backup_directory: Path
    cache_directory: Path
    cover_cache_directory: Path
```

### 7.3 パス生成関数

次の関数を提供する。

```python
def create_application_paths(
    root_directory: Path | None = None,
) -> ApplicationPaths:
    ...
```

責務は次のとおりとする。

* 利用者データルートを決定する。
* 各用途の絶対パスを生成する。
* パスを正規化する。
* `ApplicationPaths`を返す。

この関数は、原則としてディレクトリやファイルを作成しない。パスの決定とファイルシステム変更を分離し、単体テストを容易にする。

### 7.4 ディレクトリ作成関数

次の関数を提供する。

```python
def ensure_application_directories(
    paths: ApplicationPaths,
) -> None:
    ...
```

作成対象は次のとおりとする。

* `root_directory`
* `data_directory`
* `backup_directory`
* `cache_directory`
* `cover_cache_directory`

すべて`parents=True`、`exist_ok=True`で作成する。同名の通常ファイルが存在する場合など、作成できない場合は例外を呼び出し側へ通知する。

### 7.5 モジュールインポート時の副作用禁止

`paths.py`をインポートしただけで、次を行ってはならない。

* ディレクトリ作成
* データベース作成
* 既存データ移行
* 環境変数の変更

起動時の処理順序を明確にするため、ファイルシステムへの変更は明示的な関数呼び出しで実行する。

### 7.6 `PROJECT_ROOT`の扱い

`PROJECT_ROOT`は、利用者データの正式な保存先として使用しない。

旧データ検出や開発用リソース参照のためにプロジェクトルートが必要な場合は、利用者データパスとは別の概念として扱う。

PyInstaller実行時の一時展開先や実行ファイル配置先を、利用者データルートとして使用してはならない。

## 8. 旧保存先

### 8.1 正式な移行元

Version 1.9以前の正式な移行元は、起動用`main.py`が存在するプロジェクトルートを基準とする。

```text
<旧ルート>\
├── data\
│   └── books.db
├── backups\
└── cache\
    └── covers\
```

### 8.2 旧ルートの決定

ソース版では、リポジトリ直下の`main.py`を基準として旧ルートを決定する。

配布版では、インストール先に旧データが存在することを前提としない。Version 1.9以前は正式なインストーラーを提供していないため、配布版の初回起動だけで任意の開発フォルダを探索しない。

既存利用者がVersion 2.0へ移行する場合は、Version 2.0のソース版を旧プロジェクトルートから一度起動する方法、または詳細な手動移行手順をREADMEへ記載する。

実装で安全かつ一意に旧ルートを決定できる場合に限り、配布版からの自動検出範囲を拡張する。

### 8.3 探索範囲

旧データを検出するために、利用者のホームディレクトリ全体やドライブ全体を再帰探索してはならない。

自動検出は明示的に決定した一つの旧ルートだけを対象とする。

### 8.4 `book_manager.db`の扱い

旧`paths.py`には`data/book_manager.db`という定義があるが、正式な`main.py`では使用されていない。

そのため、自動移行対象の第1候補は`data/books.db`とする。

`data/book_manager.db`が存在する場合の扱いは次のとおりとする。

* `books.db`だけが存在する場合は、`books.db`を移行する。
* `book_manager.db`だけが存在する場合は、Book Manager用の有効なSQLiteデータベースであることを検証してから移行候補とする。
* 両方が存在する場合は自動選択せず、利用者へ案内して終了する。
* どちらも存在しない場合は、新規利用として処理する。

意図しないデータベースを選択して上書きするよりも、曖昧な場合に処理を停止することを優先する。

## 9. データ移行の設計

### 9.1 配置先

移行処理は、専用Serviceへ配置する。

```text
src/book_manager/services/data_migration_service.py
```

GUI、Repositoryおよび既存の`BackupService`へ移行判定を混在させない。

### 9.2 Serviceの責務

`DataMigrationService`は、次の責務を持つ。

1. 旧保存先の存在確認
2. 移行先の状態確認
3. 移行要否の判定
4. 移行元データベースの検証
5. SQLite Backup APIによるデータベース複製
6. 複製後データベースの検証
7. バックアップファイルの複製
8. 表紙画像キャッシュの複製
9. 表紙画像パスの互換処理
10. 一時ファイルの後始末
11. 移行結果の返却

利用者へのメッセージ表示はServiceの責務に含めない。

### 9.3 移行結果

移行結果は、文字列や真偽値だけでなく、不変の結果Modelとして返す。

配置先は次のとおりとする。

```text
src/book_manager/models/data_migration_result.py
```

想定する情報は次のとおりとする。

```python
@dataclass(frozen=True, slots=True)
class DataMigrationResult:
    status: DataMigrationStatus
    source_database_path: Path | None
    destination_database_path: Path
    migrated_backup_count: int = 0
    migrated_cover_count: int = 0
    warnings: tuple[str, ...] = ()
```

状態は少なくとも次を区別する。

| 状態 | 意味 |
| --- | --- |
| `NOT_NEEDED` | 新保存先のデータベースが既に存在する |
| `NO_LEGACY_DATA` | 移行元が存在せず、新規利用として開始する |
| `MIGRATED` | データベース移行が完了した |
| `MIGRATED_WITH_WARNINGS` | DB移行は完了したが、任意データの一部に警告がある |

致命的な失敗は成功結果に含めず、専用例外として呼び出し側へ通知する。

### 9.4 移行開始条件

次をすべて満たす場合だけ、データベース移行を開始する。

* 新保存先の`books.db`が存在しない。
* 有効な旧データベースを一意に特定できる。
* 移行先ディレクトリを作成できる。

新保存先の`books.db`が0バイトであっても、既存ファイルとして扱い、自動上書きしない。異常な既存ファイルの扱いは、利用者へエラーを通知して停止する。

### 9.5 移行順序

移行は次の順序で行う。

1. 新保存先の状態を確認する。
2. 旧データベース候補を確認する。
3. 旧データベースを読み取り専用で開く。
4. SQLiteデータベースとしての整合性を検証する。
5. Book Manager用データベースであることを検証する。
6. スキーマVersionが現在のアプリケーションで扱えることを確認する。
7. 移行先と同じディレクトリに一時データベースを作成する。
8. SQLite Backup APIで一時データベースへ複製する。
9. 一時データベースの整合性と内容を検証する。
10. 一時データベースを新保存先の`books.db`へ原子的に置換する。
11. 新データベースへ通常の`initialize_database()`を適用する。
12. 旧バックアップを複製する。
13. 旧表紙画像キャッシュを複製する。
14. 表紙画像パスの互換処理を行う。
15. 移行結果を返す。

### 9.6 データベースの検証

移行前後で少なくとも次を確認する。

* `PRAGMA integrity_check`の結果が`ok`である。
* `book_items`テーブルが存在する。
* `PRAGMA user_version`を取得できる。
* スキーマVersionが現在の`SCHEMA_VERSION`を超えていない。

移行元のスキーマVersionが古い場合は、複製を完了した後、新保存先だけに`initialize_database()`を実行して現在Versionへ移行する。旧データベースのスキーマは変更しない。

### 9.7 一時ファイル

データベース移行中は、完成前のデータを正式な`books.db`として公開しない。

一時ファイル名の例は次のとおりとする。

```text
books.db.migrating
```

一時ファイルは移行先と同じディレクトリへ作成し、検証成功後に`Path.replace()`で正式名へ変更する。

移行失敗時は一時ファイルを削除する。削除にも失敗した場合は警告を記録するが、旧データベースには触れない。

### 9.8 元データの保護

移行処理では、旧保存先に対して次を行ってはならない。

* ファイル削除
* ファイル移動
* データ更新
* スキーマ更新
* ファイル名変更
* バックアップ世代整理

移行元データベースは読み取り専用接続で開く。

### 9.9 新保存先が既に存在する場合

新保存先に`books.db`が存在する場合は、旧データの有無にかかわらず移行しない。

これは、Version 2.0で登録した新しいデータを、古いデータで上書きしないためである。

旧データと新データの統合はVersion 2.0の自動移行対象外とする。

### 9.10 再実行

一度移行が完了すると新保存先に`books.db`が存在するため、次回以降は`NOT_NEEDED`となる。

移行済みフラグだけに依存せず、正式なデータベースの存在と検証結果を基準に判定する。

## 10. バックアップの移行

### 10.1 対象

旧`backups`ディレクトリ直下に存在し、既存`BackupService`の命名規則に合うファイルを対象とする。

```text
books_YYYYMMDD_HHMMSS.db
```

### 10.2 方針

* 通常ファイルだけを対象とする。
* サブディレクトリは対象外とする。
* 同名ファイルが新保存先にない場合だけ複製する。
* 同名ファイルが存在する場合は上書きしない。
* 移行元ファイルを削除しない。
* シンボリックリンクは自動移行対象外とする。
* 個別ファイルの複製失敗は警告として記録する。

### 10.3 失敗時の扱い

バックアップは補助データであるため、データベース移行の完了後に一部のバックアップ複製へ失敗しても、新データベースを削除しない。

この場合は`MIGRATED_WITH_WARNINGS`として、利用者へ旧バックアップが元の場所に残っていることを案内する。

### 10.4 世代管理

移行処理中は、既存`BackupService`の最大10世代の削除処理を実行しない。

移行直後の初回自動バックアップ時に、通常の世代管理を適用する。ただし、移行元のバックアップは削除対象にならない。

## 11. 表紙画像キャッシュの移行

### 11.1 対象

```text
<旧ルート>\cache\covers\
```

直下の通常ファイルを対象とする。

### 11.2 方針

* 新保存先の`cache\covers`へ複製する。
* 同名ファイルが存在する場合は上書きしない。
* 旧ファイルを削除しない。
* サブディレクトリとシンボリックリンクは対象外とする。
* キャッシュ移行失敗だけを理由にデータベース移行を取り消さない。
* 失敗した画像は外部サービスから再取得できるものとして扱う。

### 11.3 データベース内の表紙画像パス

現在の`cover_image_path`には、次のような相対パスが保存されている。

```text
cache/covers/<ファイル名>
```

Version 2.0では、表紙画像パスを利用者データルートからの相対パスとして扱う。

正式な保存形式は次のとおりとする。

```text
cache/covers/<ファイル名>
```

絶対パスをデータベースへ新規保存しない。絶対パスは、インストール先、利用者名またはドライブが変わると無効になるためである。

### 11.4 表示時の解決

GUIが`Path(cover_image_path)`を直接参照する処理は、利用者データルートを基準に解決する処理へ変更する。

想定する規則は次のとおりとする。

1. パスが相対パスの場合は、利用者データルートを基準に解決する。
2. Version 2.0で許可する相対パスが`cache/covers`配下に収まることを確認する。
3. 既存データに絶対パスがある場合は、そのファイルが存在するときだけ互換目的で読み込む。
4. ファイルが存在しない場合は「画像なし」として扱う。
5. パス文字列だけを理由にアプリケーションを異常終了させない。

相対パスに`..`が含まれ、利用者データルート外を参照する場合は読み込まない。

### 11.5 新規取得時の保存値

`CoverImageService`は、実ファイルの絶対パスを内部で使用してよい。ただし、BookServiceへ渡してデータベースに保存する値は、利用者データルートからの相対パスへ変換する。

保存例は次のとおりとする。

```text
cache/covers/0123456789abcdef.jpg
```

パスの保存形式変換は、GUIへ分散させず、専用のパス変換処理へ集約する。

## 12. 起動処理

### 12.1 処理順序

Version 2.0の起動順序は次のとおりとする。

1. 利用者データパスを決定する。
2. 必要なディレクトリを作成する。
3. 旧保存先を決定する。
4. 既存データ移行を実行する。
5. 新保存先のデータベースを初期化する。
6. `BackupService`を生成する。
7. 起動時バックアップを実行する。
8. Repositoryおよび各Serviceを生成する。
9. Tkinterのルートウィンドウを生成する。
10. 移行結果または警告を表示する。
11. `BookManagerApplication`を生成する。
12. メインループを開始する。

移行前に空の新データベースを作成すると、移行不要と誤判定される。そのため、`initialize_database()`は移行判定より後に実行する。

### 12.2 `main.py`の変更

次のハードコードを削除する。

```python
Path("data/books.db")
Path("backups")
Path("cache/covers")
```

代わりに、`ApplicationPaths`から次を注入する。

| 対象 | 注入する値 |
| --- | --- |
| `initialize_database` | `database_path` |
| `BackupService` | `database_path`、`backup_directory` |
| `BookRepository` | `database_path` |
| `ReadingHistoryRepository` | `database_path` |
| `CoverImageService` | `cover_cache_directory` |
| GUIの表紙画像解決 | `root_directory`または専用Resolver |

### 12.3 起動時補助処理

`startup.py`には、移行Serviceを安全に呼び出し、結果または例外を起動処理へ返す補助関数を追加できる。

ただし、例外を無条件に握りつぶさない。データベース移行の失敗は、自動バックアップ失敗より重大である。

### 12.4 エラーごとの起動可否

| 状況 | 起動 | 動作 |
| --- | --- | --- |
| 新保存先決定失敗 | 不可 | エラー表示後に終了 |
| 必須ディレクトリ作成失敗 | 不可 | エラー表示後に終了 |
| 旧DBなし | 可 | 新規DBを作成 |
| DB移行成功 | 可 | 移行完了を通知 |
| DB移行失敗 | 原則不可 | 元データ保護を案内して終了 |
| バックアップ移行の一部失敗 | 可 | 警告を表示 |
| キャッシュ移行の一部失敗 | 可 | 警告を表示 |
| 起動時自動バックアップ失敗 | 可 | 既存仕様どおり警告を表示 |

DB移行失敗後に空の新規データベースを自動作成して起動すると、利用者が既存データを失ったと誤認するため行わない。

## 14. セキュリティと安全性

### 14.1 パストラバーサル対策

データベースに保存された相対パスを解決するときは、正規化後のパスが許可されたキャッシュディレクトリ配下にあることを確認する。

### 14.2 シンボリックリンク

旧バックアップと旧キャッシュの移行では、シンボリックリンクをたどらない。

意図しない外部ファイルの複製を防ぐため、通常ファイルだけを対象とする。

### 14.3 上書き防止

既存ファイルを自動上書きしない。

特に次は、存在した時点で保護対象とする。

* 新保存先の`books.db`
* 同名のバックアップファイル
* 同名の表紙画像ファイル

### 14.4 移行元と移行先の同一性

正規化した移行元と移行先が同一の場合は、移行を実行しない。

### 14.5 ファイル権限

利用者単位の`LOCALAPPDATA`を使用し、通常利用で管理者権限を要求しない。

## 15. 既存機能との整合性

### 15.1 Database

`create_connection()`と`initialize_database()`は、引数として渡されたパスを使用する現在の構造を維持する。

保存先の決定責務をDatabase層へ追加しない。

### 15.2 Repository

`BookRepository`と`ReadingHistoryRepository`は、これまでどおりコンストラクタでデータベースパスを受け取る。

Repositoryは`LOCALAPPDATA`や環境変数を参照しない。

### 15.3 BackupService

`BackupService`は、これまでどおりデータベースパスとバックアップディレクトリを受け取る。

バックアップ作成、復元元検証、復元前安全バックアップおよび世代管理の仕様を維持する。

### 15.4 CoverImageService

`CoverImageService`は、絶対パスとして解決された表紙画像キャッシュディレクトリを受け取る。

画像取得、Content-Type検証、ファイル名生成およびキャッシュ再利用の仕様を維持する。

### 15.5 CSV

CSVに`cover_image_path`は含めない現在の仕様を維持する。したがって、CSV互換性への影響はない。

### 15.6 SQLiteスキーマVersion

本機能だけを理由にスキーマVersionを変更しない。

`cover_image_path`の文字列表現を更新する必要がある場合も、テーブル構造は変わらないため、起動時のデータ移行処理として扱う。

## 17. 自動テスト

### 17.1 パス設定

少なくとも次を確認する。

* `LOCALAPPDATA`から正しい利用者データルートを生成する。
* `BOOK_MANAGER_HOME`が`LOCALAPPDATA`より優先される。

* `LOCALAPPDATA`未設定時に明確な例外を発生させる。
* 各パスが絶対パスになる。
* データベース名が`books.db`になる。

* カレントディレクトリを変更しても結果が変わらない。

### 17.2 移行不要と新規利用

* 新旧どちらにもDBがない場合、`NO_LEGACY_DATA`になる。
* 新DBが存在する場合、旧DBがあっても`NOT_NEEDED`になる。
* 新DBを上書きしない。
* 新DBが0バイトまたは不正な場合、旧DBで自動上書きしない。

### 17.3 データベース移行

* 有効な`data/books.db`を新保存先へ移行できる。

* 複数回実行しても二重移行しない。
