# book_manager 開発ロードマップ

## 1. 目的

本ロードマップは、book_managerの各Versionにおける完成条件と、今後検討・実装する機能を整理するためのものである。

Version 1.0では、書籍情報の登録・編集・検索・外部書誌情報取得を中心とした基本機能を、日常的に安心して利用できる品質まで仕上げた。

Version 1.1ではデータ保護と日常利用を改善し、Version 1.2では検索と一覧操作を改善した。

Version 1.3では、登録済み書籍の状態をより分かりやすく管理できるよう、蔵書の状態管理と日常利用の改善を進める。

---

## 2. Version 1.0 完成方針

Version 1.0では、次の状態を完成条件とした。

* [x] 書籍情報を安全に登録・更新・削除できる。
* [x] ISBNから外部書誌情報を取得できる。
* [x] 表紙画像を取得・保存・再表示できる。
* [x] 登録済み書籍を複数の検索項目から検索できる。
* [x] 一覧を任意の項目で並べ替えできる。
* [x] 検索結果を維持したまま並べ替えできる。
* [x] 入力ミスや外部サービス障害時に適切なエラー表示が行われる。
* [x] 既存データを維持したままDBスキーマを更新できる。
* [x] 自動テストによって主要機能の回帰を検出できる。

## 15. Version 2.0

### 15.1 テーマ

Version 2.0では、Windows向け配布・導入の正式対応に取り組む。

これまでの書籍管理機能を大きく増やすのではなく、Pythonや開発環境を用意していない利用者でも、安全かつ迷わず導入・起動・更新できるWindowsデスクトップアプリケーションとして完成させる。

Version 2.0のテーマは、次のとおりとする。

> 開発環境で動くアプリケーションから、安心して導入・更新できるWindowsアプリケーションへ移行する。

### 15.2 Version 2.0で解決する課題

現在は、主に次の課題がある。

* Pythonと依存パッケージを事前に導入する必要がある。
* 仮想環境を有効化し、`python main.py`を実行する必要がある。
* データベース、バックアップおよび表紙画像キャッシュの保存先が、起動時のカレントディレクトリに依存している。
* `config/paths.py`の定義と`main.py`の実際の保存先が一致していない。
* `config/paths.py`では`data/book_manager.db`、`main.py`では`data/books.db`が使用されている。
* アプリケーション本体と利用者データの配置場所が明確に分離されていない。
* 更新やアンインストール時に、利用者データをどのように維持するかが定義されていない。
* 配布物の作成方法と動作確認手順が標準化されていない。

Version 2.0では、最初に保存先の責務を整理し、その後で実行ファイル化とインストーラー作成を進める。

### 15.3 利用者データの保存先

Windowsでは、利用者データを原則として次の配下へ保存する。

```text
%LOCALAPPDATA%\book_manager\
├── data\
│   └── books.db
├── backups\
└── cache\
    └── covers\
```

この保存先には、次の方針を適用する。

* データベース、バックアップおよび表紙画像キャッシュを、アプリケーションのインストール先から分離する。
* ソースコードから起動する場合と配布版から起動する場合で、同じ既定保存先を使用する。
* 保存先の決定処理を`src/book_manager/config/paths.py`へ集約する。
* `main.py`から保存先のハードコードを取り除く。
* 必要なディレクトリは起動時に安全に作成する。
* テストでは一時ディレクトリを明示的に指定し、実利用データへアクセスしない。
* 実行場所やカレントディレクトリを変更しても、同じ利用者データを参照できるようにする。

開発・テスト・障害調査で保存先を切り替える必要がある場合に備え、環境変数による明示的な上書きも詳細設計で検討する。

### 15.4 既存データの移行

Version 1.9以前から利用しているデータを失わないことを最優先とする。

初回起動時に新しい保存先へデータベースが存在せず、従来の`data/books.db`が存在する場合は、既存データを新しい保存先へ安全に移行する。

移行には、次の方針を適用する。

* 元のデータを削除または移動せず、コピーとして残す。
* データベースはSQLiteのバックアップ機能を使用し、整合性を保って複製する。
* 新しい保存先にデータベースが存在する場合は、自動的に上書きしない。
* 同じ移行処理を複数回実行しても結果が変わらないようにする。
* 移行に失敗した場合は、元のデータと移行先の正常なデータを破壊しない。
* 従来のバックアップと表紙画像キャッシュも、可能な範囲で引き継ぐ。
* データベースに保存された表紙画像パスと、新しいキャッシュ保存先との互換性を維持する。
* 移行結果またはエラーを利用者が把握できるようにする。

Version 2.0は保存場所と配布方法の変更を中心とするため、書籍管理データのスキーマVersionは、必要がない限りVersion 7を維持する。

### 15.5 Windows実行ファイル

PythonをインストールしていないWindows環境でも起動できる実行ファイルを作成する。

実行ファイル化には、次の方針を適用する。

* PyInstallerを使用する。

* Tkinter、Pillow、Requests、証明書情報など、実行に必要な依存物を確実に含める。
* アプリケーション名、Version情報およびアイコンを設定する。
* 開発環境からの起動と配布版からの起動で、同じ機能とデータ形式を維持する。
* ビルド手順をスクリプトまたは設定ファイルとして再現可能にする。

### 17.1 テーマ

### 17.2 現状と対象範囲

Version 2.1時点の`BackupService`は、既定で24時間間隔・最大10世代を扱う。`create_backup_if_needed()`は必要性を判定し、`create_backup()`は間隔を問わず作成する。復元前には現在のDBを強制バックアップし、復元元を世代整理の対象から保護する。Version 2.1の設定画面にはバックアップフォルダーの表示・開く操作があるが、作成日時・件数・設定値・手動作成操作はない。

Version 2.2では次を対象とする。

* [x] 最後に作成されたバックアップの日時、保存先、バックアップ件数を設定画面に表示する。対象がない場合は「バックアップなし」と明示する。表示する日時の根拠（ファイル名と実ファイルの存在）を定義し、ファイルが存在することと復元可能性を混同しない。
* [x] 設定画面に「今すぐバックアップ」を追加し、既存の`create_backup()`を利用する。作成成功・失敗・対象DBなしを区別して表示し、成功後は状態表示を更新する。
* [x] 自動バックアップ間隔と保持世代数を変更・保存できるようにする。未設定時の既定値は24時間・10世代とし、入力可能範囲と単位を固定する。
* [x] 保存した設定を次回起動時の`BackupService`生成に反映する。起動中に変更した値と、次回起動時に適用する値の扱いを画面に明記する。

### 17.3 安全性と設定保存

* バックアップ設定は利用者データ領域の`backup_settings.json`へ保存する。通常は`%LOCALAPPDATA%\book_manager\backup_settings.json`とし、`BOOK_MANAGER_HOME`指定時はその配下を使う。原子的に置き換え、APIキーは複写しない。更新・アンインストール・再インストール後の保持は配布版でも確認する。
* 不正な入力は保存前に拒否し、読み込み失敗・破損・書き込み失敗を利用者が認識できるようにする。設定保存に失敗しても従来の正常な設定ファイルを壊さない。
* 保持世代数を減らしただけでは既存バックアップを削除しない。世代整理は新しいバックアップの作成が成功した後にのみ実行する。作成失敗時は以前のバックアップを維持する。
* 復元前の強制バックアップと、選択された復元元の保護を維持する。通常の世代整理と復元時の保護の優先関係をテストで固定する。
* Version 2.1のファイル名は秒単位である。同じ秒の連続作成でも既存バックアップを上書きしない一意な命名を採用する。

### 17.4 自動バックアップと手動バックアップの境界

自動バックアップはこれまでどおり起動時に必要性を判定する。間隔が経過した瞬間に、起動中のアプリが自動で作成する常駐スケジューラは追加しない。「今すぐバックアップ」は間隔と無関係に作成するが、成功したバックアップは次回の自動判定の基準になる。復元前の安全バックアップは手動・自動設定にかかわらず必須とする。
